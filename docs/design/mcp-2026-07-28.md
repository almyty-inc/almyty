Status: accepted (all 16 decisions as recommended). P0 built on `feat/mcp-p0`: protocol core in
`backend/src/modules/mcp/core/`, CIMD/`iss`/`application_type`, conformance in CI. P1 built: the
runner transport split on `feat/mcp-p1-runner` (`/runners/stream`), the 2026-07-28 stateless era
on `feat/mcp-p1` (server/discover, per-request `_meta`, header checks, error ranges, caching

`isError: true`, not `failed` (the extension reserves `failed` for JSON-RPC errors). P2 client side
(mcp-sources, OAuth client) and the stdio proxy are separate branches. Code-mode staging over
`input_required` waits for code mode.

Recon baseline: `development` at `b0281c1a` (2026-10-01).

## In plain words

An almyty MCP gateway is the address you paste into Claude Code, Cursor, Codex, Pi or Claude
Desktop so that the assistant can use your tools. Those assistants speak a protocol called MCP,
and MCP has changed three times since the version our gateways speak. The newest version
(2026-07-28) changes how a connection works at its root: there is no opening handshake anymore,
every request carries everything the server needs to know, and the server keeps no memory of the
client between requests.

What changes for a user:

- **Today**, a current assistant connects, but our gateway answers in a 2025-03-26 dialect. It
  works because clients are lenient. As clients drop the old dialect, it stops working.
- **After P0**, the gateway speaks the same language as today's clients. Tools show a readable
  title, say whether they only read data or can change or delete it, return structured data next
  to text, and sign-in works through the newer client registration that does not need a manual
  step.
- **After P1**, the gateway also speaks the 2026 dialect. Clients that have moved on keep working,
  older ones keep working, and the gateway can tell a client when its tool list has changed.
- **After P2**, a long agent run started from an assistant does not time out. The assistant gets
  a ticket, checks back, and if the agent needs an answer or an approval, the assistant asks the
  person and sends the answer back. MCP servers you connect to almyty get the same treatment from
  our side.

Nothing changes in the URL a user pastes. One endpoint serves every version, picked per request.

- **R2. There is no "TOOLS gateway".** `GatewayType` (`backend/src/entities/gateway.entity.ts`) has

- **R3. Gateway MCP is not session-based today.** The session-based, Redis-backed transport

## Architecture: one protocol core

The owner's principle is one protocol core for every MCP surface. Today there are three
dispatchers (`McpService.handleJsonRpc`, `AlmytyMcpService.dispatch`, `SseTransport`) and three
places that handle batching and session headers.

Proposed shape, all inside `backend/src/modules/mcp/core/`:

```
HTTP request
  -> McpHttpBinding            origin check, header parsing, status codes, JSON or SSE framing
  -> McpProtocolCore           version resolution, envelope validation, method table,
                               result decoration (resultType, _meta.serverInfo, ttlMs/cacheScope),
                               error mapping per version, request log (version, clientInfo, trace)
  -> McpSurface (interface)    listTools, callTool, listResources, readResource, listPrompts,
                               getPrompt, complete, plus capabilities and instructions
       GatewaySurface          tenant gateway (today's McpToolHandler + McpContentHandler)
       OrgSurface              gateway-less POST /mcp (same handlers, no gateway)
       ManagementSurface       today's AlmytyMcpService.exec, minus its own dispatch
```

The surfaces never see protocol versions. The core translates once: for example a surface returns
`{ content, structured, isError }` and the core emits `structuredContent` only when the version is
2025-06-18 or later. Per-version differences sit in one table (`core/versions.ts`), not in `if`
chains across handlers.

The stdio proxy cannot import backend code; it uses the official SDK (see "Client side") and talks
to the core over HTTP like any other client.

## Runner transport split

This happens first, before any P1 change touches sessions, so runners keep working unchanged.

What the runner depends on today (`packages/runner/src/streamable-client.ts`,
`backend/src/modules/mcp/transports/streamable-http.transport.ts`):

- `POST /mcp/streamable` with worker envelopes (`v: 1`, `type`), JWT auth.
- `GET /mcp/streamable` opening an SSE stream, `Mcp-Session-Id` issued on first POST.
- `Last-Event-ID` replay from a 256-event ring buffer.
- The Redis bridge: session registry `strm:sess:<id>` (TTL 600 s), channels `strm:out` and
  `strm:resp`, so any pod can adopt a session, deliver to the pod holding the stream, and match a
  response to the pod waiting for it.
- `runner/runner-call.service.ts` and `runner/coding-relay.service.ts` subscribe to the
  transport's `envelope` event.

Plan:

1. Move the class to `backend/src/modules/runner/transport/worker-stream.transport.ts`, renamed
   `WorkerStreamTransport`. Remove the JSON-RPC branch from it. Envelopes only; a JSON-RPC body is
   refused with the existing `MALFORMED_ENVELOPE` error.
2. Serve it on a new route owned by the runner module (proposed `/runners/stream`, see
   Decisions). Keep `/mcp/streamable` routed to the same class for envelopes for one runner
   release, so an already installed runner keeps connecting.
3. Keep header names (`Mcp-Session-Id`, `Last-Event-ID`) on the worker route. They are generic
   enough, and renaming them would change the runner's reconnect code, which the acceptance
   criteria want untouched.
4. Rename the Redis keys only if the move is clean without it. Prefer keeping `strm:*` so a rolling
   deploy does not split old and new pods.
5. `packages/runner` changes only its URL (with a fallback to `/mcp/streamable` on 404 during the
   overlap). `streamable-client.spec.ts` and the backend `streamable-http.transport.spec.ts`
   move with the code, assertions unchanged.
6. `McpSessionService` stays only if something still reads it after the split; it is in-memory
   and pod-local today. The in-memory `sessions` map inside `McpService` is used only by
   `/mcp/transport/stats` and goes away with the core.

After the split, `/mcp/streamable` JSON-RPC is gone, and no MCP surface holds per-client state.
The Redis session registry serves runners only, as the owner's spec says.

## Version negotiation: several versions at once

Supported set (proposed, see Decisions): `2026-07-28`, `2025-11-25`, `2025-06-18`, plus the two
older ones we serve today, `2025-03-26` and `2024-11-05`, until the request log says they can go.

The core picks the version per request, with no session store, following the
[2026-07-28 dual-era rules](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning#backward-compatibility-with-initialization-based-versions):

1. The body has `params._meta["io.modelcontextprotocol/protocolVersion"]`: **modern**. Validate
   it against the supported modern set (else -32022 with HTTP 400), require the
   `MCP-Protocol-Version` header to match (else -32020), validate `Mcp-Method` / `Mcp-Name`.
   Serve statelessly.
2. The method is `initialize`: **legacy handshake**. Pick the client's version if it is in the
   legacy set, else our newest legacy version (2025-11-25). No session is stored: the reply
   carries an `Mcp-Session-Id` only so that clients that insist on one are satisfied, and it is
   never read back.
3. Anything else: **legacy, after the handshake**. The version is the `MCP-Protocol-Version`
   header. No header means 2025-03-26 (the spec allows this for pre-2025-06-18 clients).
   An unsupported header value gives HTTP 400.

This works without sessions because 2025-06-18 and later clients send the version header on every
request, and older ones are treated as 2025-03-26, which is exactly what today's code answers.
The one thing we lose for legacy clients is server-to-client traffic on a GET stream; we have none
today, so nothing is lost.

Request log: every MCP request records `protocolVersion`, era (`modern`, `legacy`, `assumed`),
`clientInfo.name` and `clientInfo.version` (from `_meta` or from the `initialize` params; legacy
requests after `initialize` carry no clientInfo, so we log the `User-Agent` alongside), gateway id,
method and outcome. This goes on the existing request log row
(`backend/src/common/interceptors/request-logging.interceptor.ts`, via `setProtocolContext`) and as a metric
label, so the analytics page can show a version-by-client breakdown. This lands in P0, "from day
one".

## Auth

### Client ID Metadata Documents (CIMD)

A client may send a `client_id` that is an `https` URL. The authorization server fetches that
URL and reads the client's metadata from it, instead of requiring a prior registration.

- **Advertise** `client_id_metadata_document_supported: true` in both AS metadata documents
  (`mcp-oauth-discovery.controller.ts` and the path-suffixed copy in `mcp-oauth.controller.ts`).
  A guard spec asserts the two documents stay identical.
- **Detect**: `client_id` parses as an `https` URL with a path. Anything else follows the
  registered-client path as today.
- **Fetch** through `safeFetch` (`backend/src/common/security/safe-fetch.ts`): string gate, DNS
  pin, no redirects, total deadline (5 s), response cap (64 KiB), `Accept: application/json`. No
  private-host relaxation applies, whatever `MCP_ALLOW_PRIVATE_URLS` says: that flag is for the
  outbound client, and a metadata URL arrives from an anonymous browser redirect.
- **Validate**: the document's `client_id` equals the URL exactly; `redirect_uris` is present and
  the request's `redirect_uri` is an exact member; `token_endpoint_auth_method` is `none` (or
  `private_key_jwt` with `jwks_uri`, which we do not support yet, so it is refused);
  `grant_types` and `response_types` within what we allow; `client_name` and `logo_uri` bounded
  in length. `application_type` decides the redirect rule (below).
- **Cache** by URL in Redis, honouring `Cache-Control` within a floor of 5 minutes and a ceiling
  of 24 hours. A failed refresh keeps a still-fresh entry; an expired one is refused.
- **Persist**: upsert an `oauth_clients` row with `clientId` = the URL, so authorization codes
  and tokens keep their foreign key and revocation works as for registered clients (Decisions).
  The registration cap (`MAX_CLIENTS_PER_GATEWAY`) does not apply to CIMD rows, since nobody can
  mint them in bulk without controlling distinct https URLs; a separate per-host rate limit on
  fetches does.
- **Consent screen**: show the client name *and* the host of the metadata URL, because the name
  is self-asserted (`frontend/src/pages/oauth/consent.tsx`).
- **SSRF guard tests**: metadata URL pointing at loopback, link-local, metadata IP, a public name
  resolving to a private address, a redirect to an internal host, an oversized body, a slow drip.
  Each must be refused before any socket to the internal address opens. Reuse the cases in
  `backend/src/common/security/__tests__/every-tenant-url-is-gated.spec.ts` and register the new
  call site in `outbound-transport-inventory.guard.spec.ts` next to it.

### `iss` parameter (RFC 9207)

- `issuer` in our AS metadata is the per-gateway prefix (`{base}/{org}/{gateway}`). The consent API
  (`GET /:org/:gateway/oauth-consent`) returns it, and `redirectToClient` appends `iss` to both the
  success redirect and the `access_denied` redirect.
- Advertise `authorization_response_iss_parameter_supported: true`.
- The `POST /authorize` JSON variant returns `iss` next to `code` and `state`.

### `application_type` on DCR

- `register` accepts `application_type` (`web` default, `native`), stores it on `oauth_clients`
  (migration), and echoes it in the registration response.
- `validateRedirectUri` takes the type: `web` needs `https` (loopback http only in development);
  `native` allows `http://127.0.0.1`, `http://[::1]`, `http://localhost` with any port, and
  private-use schemes. The same rule applies to CIMD documents.
- DCR stays. Docs say it is deprecated in 2026-07-28 and kept for clients that do not support CIMD.

## Stateless 2026-07-28 changes

- **`server/discover`**: served by the core for every surface. `supportedVersions` lists both
  eras, so a dual-era client can see we still speak 2025. It needs authentication like any other
  method (no scope), because capabilities differ per gateway.
- **Results**: the core adds `resultType`, `_meta["io.modelcontextprotocol/serverInfo"]` (gateway
  name as `name`, almyty version as `version`) and, on the five cacheable results, `ttlMs` and
  `cacheScope`.
- **Headers**: `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`, decoded and compared to the body
  before auth scope checks and before dispatch. Header failures are 400 + -32020 with the request
  `id` when parseable.
- **Status codes**: unknown method 404 + -32601; GET and DELETE 405; notifications 202.
- **SSE responses**: allowed per request. We answer JSON, except `subscriptions/listen` and long
  `tools/call` with progress, which use SSE with `X-Accel-Buffering: no` (nginx) and a keep-alive
  comment every 15 s, as the worker transport already does.
- **Cancellation**: on 2026, a closed response stream cancels the call. `tool-executor` already
  takes an `AbortSignal`, and
  `gateways/__tests__/streamed-execution-stops-with-its-client.spec.ts` pins the same rule for
  streamed agent executions behind a gateway; wire the same for MCP.
- **`subscriptions/listen`**: one SSE response per listen request, acknowledged with
  `notifications/subscriptions/acknowledged`, filtered to the opted-in types
  (`toolsListChanged`, `promptsListChanged`, `resourcesListChanged`, `resourceSubscriptions`), each
  notification tagged with `io.modelcontextprotocol/subscriptionId`. The producer side is a Redis
  channel `mcp:changed:<gatewayId>`, so the pod holding the listen stream hears a change made on
  any pod. This also gives the Tasks extension its optional `notifications/tasks`.
- **ping, logging/setLevel**: gone for 2026 (404). `notifications/message` is sent only when the
  request carried `io.modelcontextprotocol/logLevel`; we send none.
- **Trace context**: `traceparent`, `tracestate`, `baggage` from `_meta` are validated (W3C
  format), put into the request context (`backend/src/common/request-context.ts`), and written to the request
  log, the audit row metadata and the tool execution record. When an exporter exists, spans
  continue the client's trace.

## Agent runs as tasks and `input_required`

### `invoke_agent` returns a task

- When the request declares `io.modelcontextprotocol/tasks` and the agent runs on the autonomous
  runtime, `invoke_agent` answers `resultType: "task"` with `taskId` = the run id, `status:
  working`, `ttlMs` (the run's retention class) and `pollIntervalMs` (2000).
- `tasks/get` maps `AgentRunStatus` (`backend/src/entities/agent-run.entity.ts`):
  `pending`, `running`, `sleeping` give `working`; `waiting_input` and `waiting_approval` give
  `input_required` with `inputRequests`; `completed` gives `completed` with the `CallToolResult`
  `invoke_agent` would have returned; `failed` and `timeout` give `completed` with that result
  marked `isError: true` (as built: the extension reserves `failed` for JSON-RPC errors);
  `cancelled` gives `cancelled`.
- `tasks/update` takes `inputResponses` and resumes the run (the same entry points the dashboard
  uses for answers and approvals). `tasks/cancel` cancels the run.
- Authorization: a task is readable and updatable only by the principal that started it (same
  user, same gateway), checked on every call. Run ids are not secrets.
- Workflow agents still run synchronously. A workflow that exceeds the request deadline could
  return a task too; out of scope here.
- For clients without the extension, which per D8 is every mainstream client today, `invoke_agent`
  keeps returning the run id, and the management surface gains `get_run` and `answer_run` tools.
  This is the only way those clients can follow a run at all today.

### `input_required` for `ask_user` and approvals

MRTR works on `tools/call`, `resources/read` and `prompts/get`. The server returns
`resultType: "input_required"` with `inputRequests` (here: `elicitation/create`) and a
`requestState`; the client asks the person and retries the same call with `inputResponses` and the
same `requestState`.

- **ask_user inside a task**: `tasks/get` returns `input_required` with an
  `elicitation/create` built from the question (a one-field form). `tasks/update` delivers the
  answer.
- **ask_user without tasks, on a 2026 client that declares elicitation**: `invoke_agent` may wait
  for the run up to a short deadline (proposed 25 s). If the run reaches `waiting_input` inside
  that window, the call returns `input_required`; the retry carries the answer, resumes the run and
  waits again. Past the deadline it returns the run id as today.
- **Held tool calls (#886)**: today a gateway or MCP caller gets `isError` text plus an
  `_approvalId` to call again with. On 2026 clients the same hold becomes `input_required`:
  - `requestState` carries the approval id, the tool, the parameter fingerprint, the principal and
    an expiry, sealed with AES-GCM under a server key (the MRTR page requires integrity protection
    when the state influences authorization, and binding to principal, request and TTL).
  - `inputRequests` asks the person to confirm, showing the change: tool title, the amount rule
    that fired, the arguments.
  - The retry checks the seal, then asks `ToolApprovalGateService` (`tools/tool-approval-gate.service.ts`) for the
    approval state. Who may
    approve through this path is a Decision: by default only a person who could approve the
    request in Approvals.
  - Legacy clients keep the `_approvalId` text path unchanged.
- **Code-mode staging**: the code-mode change set (code-mode part D) uses the same mechanism with
  the change set as the form, so any 2026 client can approve staged writes.
- Elicitation must be declared in the request's client capabilities; without it the server falls
  back to the legacy text answer, as the MRTR page requires.

## Client side (mcp-sources, connection probe, stdio proxy)

### mcp-sources and the connection probe

- One client, used by both: `connection-validation.service.ts` stops building its own
  `initialize`, and calls `McpClientService`.
- Dual-era per the spec: try a modern request first (`server/discover` with `_meta`). A recognized
  modern error means a modern server (retry with a version from `supported`); anything else
  (4xx without a modern JSON-RPC body) means legacy, so fall back to `initialize`. Cache the era
  per origin on the source row (`serverInfo.protocolVersion` exists already).
- Modern path: per-request `_meta`, `Mcp-Method`, `Mcp-Name`, `Mcp-Param-*` for remote tools
  that declare `x-mcp-header` (reject tools with invalid annotations, as the spec requires),
  `resultType` handling.
- Store `outputSchema`, `annotations`, `title`, `icons` on the generated tool (`tool.outputSchema`
  relation, plus `configuration.mcp` for the rest), and feed the annotations into the
  side-effect class (code-mode part A).
- `input_required` from a remote: inside an agent run, `elicitation/create` maps onto `ask_user`
  (the run goes to `WAITING_INPUT` with the remote's question and resumes with the retry);
  `sampling/createMessage` is refused (we do not add Sampling); `roots/list` answers empty.
  Outside a run (tool Test button, gateway passthrough), the result is an `isError` explaining
  that the remote needs input.
- Remote tasks: declare the extension, poll `tasks/get` within the run's deadline, cancel on run
  cancel.
- OAuth client, a new connect method on the `mcp-custom` connector:
  - PRM discovery from the 401's `resource_metadata`, then AS metadata (RFC 8414, OIDC fallback).
  - Registration order: pre-registered client if configured, else CIMD (we host an almyty client
    metadata document at a stable URL on the API origin), else DCR with
    `application_type: "web"`.
  - PKCE S256, `resource` (RFC 8707) on authorize and token, validate `iss` when present.
  - Tokens stored in `credentials`, keyed by issuer: a source whose AS changes must reconnect
    (SEP-2352). This fits the Connections rule that every third-party secret lives in
    `credentials`.

### stdio proxy (`packages/mcp-server`)

- Move from `@modelcontextprotocol/sdk` 1.x to the v2 packages (`@modelcontextprotocol/server`;
  the SDK's `docs/migration/support-2026-07-28.md` covers it). Confirm before release that the v2
  stdio server still serves a legacy `initialize`, because Claude Desktop and others may send it
  for a while.
- Keep the #875 behaviour: no `list_changed` before the client is ready. In 2026 that means no
  notifications outside a `subscriptions/listen` stream.
- Upstream, the proxy becomes a modern client of our core (it sends no `initialize` today, which
  the core's rule 3 treats as legacy 2025-03-26; after P1 it sends `_meta`).
- Carry `outputSchema`, `annotations`, `title` from upstream into its registrations instead of
  rebuilding only a zod input shape (`schema.ts`).

## Risks

- **Clients lag the spec.** No client in the official matrix supports Tasks, and elicitation
  support varies by client. Mitigation: every new pattern has a legacy answer (run id plus
  `get_run`; `_approvalId` text), and acceptance for tasks and `input_required` runs with the SDK
  v2 client and Inspector, not with Claude Code.
- **Pi has no native MCP.** It reaches MCP servers through a community extension
  ([pi-mcp-extension](https://pi.dev/packages/pi-mcp-extension), or `pi-mcp-adapter`). The
  "works in Pi" criterion tests that extension's version, not Pi.
- **Conformance for 2026 is alpha.** A suite that changes under us can turn CI red for reasons
  outside our code. Mitigation: pin, run non-blocking until a stable release covers 2026-07-28.
- **Dual-era bugs.** A request that looks modern and legacy at once (an `initialize` that carries
  `_meta`) must take one path deterministically. Mitigation: the precedence order above, pinned
  by tests.
- **Header checks behind proxies.** nginx and the k8s ingress must pass `Mcp-*` headers and not
  buffer SSE. `X-Accel-Buffering: no` and a staging check per route.
- **CIMD as an SSRF and phishing vector.** Any https URL becomes a client. Mitigation: `safeFetch`
  with no relaxation, short caps, per-host fetch rate limit, host shown on the consent page.
- **Runner overlap window.** Installed runners use `/mcp/streamable`. Mitigation: alias for one
  release and a URL fallback in the new runner.
- **JSON Schema rewrite.** Normalising OpenAPI 3.0 schemas can change what validates. Mitigation:
  validate every stored tool schema before and after in a migration-style spec; ship the rewrite
  on output only, never stored.
- **Scope of P2 client-side OAuth.** It is a full OAuth client (discovery, CIMD, DCR, PKCE,
  issuer binding), larger than the owner's spec implies. It may need its own phase.

## Decisions for Frane

Each has a recommended option. None is decided in this doc.

1. **Queue order.** Put MCP compliance first, ahead of hosted runners, always-on and code mode, as
   the spec proposes. *Recommended: yes.* Code-mode part F depends on P0.
2. **Versions served.** Serve 2026-07-28, 2025-11-25 and 2025-06-18 as claimed versions, and
   keep answering 2025-03-26 and 2024-11-05 as unclaimed legacy until the request log shows no
   use. *Recommended: yes; review the log 60 days after P1 ships.*
3. **Runner route.** Move the worker transport to a runner-owned route. *Recommended:
   `/runners/stream`, with `/mcp/streamable` kept for envelopes (only) for one runner release.*
4. **Gateway-less MCP endpoints.** `POST /mcp` (used by the stdio proxy without a gateway), the
   per-method REST routes (`/mcp/tools/list`, ...), `/mcp/sse`, `/mcp/servers/:id/sse` and JSON-RPC
   on `/mcp/streamable`. *Recommended: keep `POST /mcp` on the core as the org surface; remove
   JSON-RPC from `/mcp/streamable` with the split; keep `/mcp/sse` as deprecated; remove the
   per-method REST routes.*
5. **"TOOLS gateway".** No such gateway type exists. *Recommended: read it as the gateway-less org
   surface (`POST /mcp`); if a new gateway type was meant, that is a separate spec.*
6. **Who can approve through `input_required`.** *Recommended: only a person who could approve the
   request in Approvals (approver role on the policy). For anyone else the call keeps the
   current "waiting for approval" answer, and the approval happens in the dashboard.*
7. **Clients without the Tasks extension.** *Recommended: keep returning the run id, and add
   `get_run` and `answer_run` to the management tools in P2.*
8. **CIMD trust.** *Recommended: accept any https metadata URL behind the SSRF guard, show its
   host on the consent page, rate-limit fetches per host; no allowlist. Org owners can still
   restrict a gateway to registered clients with a gateway setting (off by default).*
9. **CIMD storage.** *Recommended: upsert an `oauth_clients` row keyed by the URL, refreshed from
   the cache, so codes, tokens and revocation work as they do for registered clients.*
10. **OTLP.** No exporter exists today. *Recommended: P1 records trace context in the request log
    and audit metadata (core). An OTLP exporter, as a fourth audit-stream target in EE
    `audit_export`, becomes its own small item outside this doc.*
11. **Client-side OAuth for mcp-sources.** *Recommended: build it as a connect method on the
    `mcp-custom` connector, reusing the Connections PKCE flow, and host the almyty client
    metadata document at a fixed URL on the API origin. Split it into its own phase (P2b) if P2
    runs long.*
12. **stdio proxy SDK.** *Recommended: migrate to SDK v2 packages in P2, but only after confirming
    the v2 stdio server still answers a legacy `initialize`. If it does not, stay on 1.x
    (2025-11-25) and revisit.*
13. **`listChanged` for legacy clients.** It needs a server stream, which needs sessions.
    *Recommended: real `listChanged` only for 2026 clients through `subscriptions/listen`; legacy
    clients keep `listChanged: false`, and GET answers 405.*
14. **Conformance in CI.** *Recommended: blocking for the 2025-11-25 suite from P0; non-blocking
    for 2026-07-28 until a stable conformance release covers it, then blocking.*
15. **`x-mcp-header` on our tools.** *Recommended: do not emit it now. We validate `Mcp-Param-*`
    if a client sends it, and support it in our client. Emitting it is only useful for
    header-routing intermediaries, which we do not have.*
16. **Our non-standard methods** (`tools/discover`, `tools/search`, `tools/get`, `skills/list`,
    `skills/get`). *Recommended: keep for legacy clients; for 2026, serve discovery through
    code-mode part B meta-tools and evaluate the official Skills over MCP extension in a separate
    spec.*
