# Control almyty via MCP

You can set up and run almyty by asking your AI assistant, instead of clicking through the dashboard. Connect an assistant such as Claude Code, Cursor or Claude Desktop to almyty, then ask in plain words: "import our orders API and publish the refund tools", or "put the support agent on Slack with a $2 limit per run". The assistant does the same things you would do in the dashboard.

This works through **MCP** (Model Context Protocol), the common way AI apps connect to outside tools. almyty is itself an MCP server.

This is different from [publishing your own tools on an MCP gateway](/gateways/mcp). There, an AI uses *your* company's tools. Here, it uses *almyty's own* tools to set almyty up.

## Connect your assistant

Add almyty to your assistant as an MCP server with the address `https://api.almyty.com/<org>/almyty`, where `<org>` is your organization's slug, and sign in once. The exact commands are under [For developers](#for-developers).

## What your assistant can do

It can do what you can do in the dashboard, except take a secret (see [What it cannot do](#what-it-cannot-do)). It has 76 tools: 71 cover the everyday jobs directly, and five more reach everything else, from rolling back an agent to a saved version to managing members, teams, approval rules and audit streams.

It acts as you. Your role and your plan apply exactly as they do in the dashboard: if the dashboard would refuse you something, your assistant is refused it too.

| Area | What it can do |
| --- | --- |
| **APIs** | Connect, update and delete APIs; import an API description and check on the import |
| **Tools** | List the tools made from your APIs, switch one on, delete one; write or change a tool by hand |
| **Tool hub** | Search ready-made templates and install one as an API with its tools |
| **Gateways** | Create, change and delete gateways, add tools to them, add or remove sign-in, create gateway keys |
| **Agents** | Create, change, switch on and off, delete and run agents, and follow a long run until it is done |
| **Channels** | Put an agent where people are: add, check, publish and unpublish channels, set branding and visitor rules, build downloadable apps |
| **Providers** | List model vendors and add keyless ones such as Ollama (a vendor's key is added in the dashboard) |
| **Models** | List models, refresh the list, check a model, preview which model an agent would use, list models on your own cloud accounts |
| **Credentials** | List the services you can connect, connect one by signing in with it, see and change who may use a credential (the secret itself is added in the dashboard) |
| **Memory** | Read, write, search and tidy up what agents remember |
| **Runners** | List your runners |
| **Organization** | List members and their roles; invite people, revoke invites, change roles and remove members; manage user accounts; create an organization or delete this one |
| **Cost** | List spending budgets and see what has been spent this period |
| **Analytics** | Get one report at a time: overview, tools, gateways, models, agent runs, alerts, routing failures |
| **Approvals** | See what is waiting for approval and approve or reject it, so a paused run carries on |
| **Everything else** | Find any other dashboard action and run it: agent versions, schedules, roles and limits; run traces; channel domains; API operations; API keys and access keys; gateway tools and keys; teams; budgets and alerts; data retention; notifications; the audit log; files; and, on plans that include them, custom roles, policies, single sign-on, your own encryption key, compliance, governance and billing |

## Examples

Ask your assistant:

```text
> Import the Stripe OpenAPI spec, then publish an MCP gateway with just the refund tools.
```

It imports the description, waits for the import, finds the refund tools, creates a gateway with them, adds a key, and hands you back a ready address, without you opening the dashboard.

Or put an agent in front of people from start to finish:

```text
> Put my support-bot agent on Slack as Acme Support, with a $2 limit per
> run, and publish it.
```

It sets the name and the limits a public channel needs, adds the Slack channel, checks it, and publishes it.

## When an agent takes a while, or needs you

An agent that works on its own can take minutes, and it may stop to ask you something or to wait for an approval. How your assistant follows the run depends on what the assistant can do:

- **Assistants that follow tasks** (MCP 2026-07-28 with the tasks extension) treat the run as a task. They check on it, show you the agent's question or the approval in their own window, and pick up the result when it is done. A long run does not time out.
- **Assistants that can ask you questions** (MCP 2026-07-28 with elicitation) wait for the run for up to 25 seconds. If it finishes, you get the answer; if the agent asks something, you are asked right there and the run carries on with your answer.
- **Every other assistant** gets the run's id straight away. It follows the run with **get_run**, answers the agent's question with **answer_run**, and decides an approval with **decide_approval**.

Only someone who could approve a request on the **Approvals** page is asked to approve it from their assistant. Anyone else is told the run is waiting for approval, and it is approved in the dashboard.

## What it cannot do

Some things are left out on purpose:

- **Take a secret.** You never give your assistant an API key, a password, a token or a client secret. Adding or changing a credential, an API's key, a provider's key or an OAuth client secret is done in the dashboard, where the secret goes straight into your credentials vault. When your assistant needs one, it gives you a link to the page where you add it.
- **Switch an agent on directly.** A new agent always starts as a draft. Switching it on runs its checks first, and only a switched-on agent can be run.
- **Sign you in or out.** Signing in and out, signing up and changing your password stay in the dashboard.

It also cannot download files or app builds directly (it gets a download link instead), and it checks on long jobs by asking for their status rather than watching a live stream.

## For developers

Add the built-in `almyty` system gateway at the universal `/mcp` endpoint:

```bash
claude mcp add almyty --transport http https://api.almyty.com/<org>/almyty
```

Or in a client config file:

```json
{
  "mcpServers": {
    "almyty": { "url": "https://api.almyty.com/<org>/almyty" }
  }
}
```

Replace `<org>` with your organization's slug. The first time your assistant connects, it opens a browser window where you sign in and approve it (MCP OAuth); the server announces itself as `almyty`. Use Streamable HTTP (`--transport http`, the address above).

This is not `https://api.almyty.com/mcp`: that address serves your organization's own API tools, the ones you publish on gateways, not the tools that manage almyty.

The management server speaks the same MCP versions as every gateway: **2026-07-28**, **2025-11-25** and **2025-06-18**, plus 2025-03-26 and 2024-11-05 for older clients (see [MCP gateway, Protocol versions](/gateways/mcp#protocol-versions)). Its tools carry titles and annotations (`list_*` and `get_*` only read, `delete_*` destructive), and a tool that returns a record also returns it as `structuredContent`. An unknown tool name is a `-32602` error. Its tool set does not change, so it reports `tools.listChanged: false` and a `subscriptions/listen` stream on it only keeps alive.

The tools, by area:

| Area | Tools |
| --- | --- |
| APIs | `create_api`, `list_apis`, `update_api`, `delete_api`, `import_schema`, `check_import_status` |
| Tools | `list_tools`, `activate_tool`, `delete_tool` |
| Tool hub | `list_tool_templates`, `install_tool_template` |
| Gateways | `create_gateway`, `list_gateways`, `delete_gateway`, `assign_tools_to_gateway`, `add_auth_to_gateway`, `remove_auth_from_gateway` |
| Agents | `create_agent`, `list_agents`, `update_agent`, `activate_agent`, `deactivate_agent`, `delete_agent`, `invoke_agent`, `get_run`, `answer_run` |
| Channels | `list_channels`, `add_channel`, `get_channel`, `check_channel`, `update_channel`, `delete_channel`, `publish_channel`, `unpublish_channel`, `get_public_settings`, `update_public_settings`, `build_channel`, `list_builds` |
| Providers | `add_provider`, `list_providers` |
| Models | `list_models`, `sync_models`, `validate_model`, `preview_model_routing`, `list_model_deployments`, `list_model_versions` |
| Credentials | `list_connectors`, `list_connections`, `start_connection`, `complete_connection`, `list_connection_grants`, `grant_connection`, `list_credentials` |
| Memory | `memory_put`, `memory_get`, `memory_list`, `memory_search`, `memory_delete`, `memory_supersede`, `memory_consolidate`, `memory_sync`, `memory_transfer`, `memory_list_backends`, `memory_backends_health` |
| Runners | `list_runners` |
| Organization | `list_org_members` |
| Cost governance | `list_budgets`, `get_spend` |
| Analytics | `get_analytics` |
| Approvals | `list_approvals`, `decide_approval` |
| Everything else | `search_operations`, `get_operation`, `call_read_operation`, `call_write_operation`, `call_destructive_operation` |

The first example chains `import_schema`, `check_import_status`, `list_tools`, `create_gateway`, `assign_tools_to_gateway` and `add_auth_to_gateway`. The second chains `update_public_settings`, `add_channel`, `check_channel` and `publish_channel`.

Editing a gateway and writing a tool by hand are operations (`gateways.update`, `tools.create`, `tools.update`). Status is not a settable field: `create_agent` always produces a draft, `activate_agent` is the only path to active because it runs pipeline validation first, and `invoke_agent` refuses an agent that is not active.

No tool or operation takes a secret as an argument. A call with a field named like one (`apiKey`, `token`, `password`, `clientSecret`, an `Authorization` header), at any depth, is refused before it runs, with a link to the dashboard page where the secret is added. `add_provider` adds keyless providers only (Ollama, or a custom endpoint without a key), and `add_auth_to_gateway` does not add `jwt`, which needs a signing secret. The operations that exist to store a secret (adding, changing or rotating a credential, setting an API's key, an OAuth client secret, visitor sign-in) are not operations; asking for one by name answers with that page.

Operations that mint a key (`profile.create_api_key`, `credentials.create_access_key`, `gateways.create_api_key`) return it once, in plaintext, exactly as the dashboard does. Deleting the organization (`organization.delete`), removing a member (`members.remove`), deleting a user (`users.delete`), turning your own encryption key off or on (`kms.set_enabled`) and changing data retention (`organization.update_retention`) are destructive: they run only through `call_destructive_operation`, so an assistant that confirms destructive tools asks you first.

### Every other operation

Everything else the REST API does for a signed-in member is an **operation**, reached through five tools instead of hundreds:

| Tool | What it does |
| --- | --- |
| `search_operations` | Search by words (`"rollback agent version"`), by `resource` (`teams`, `budgets`) or by `effect`. Returns each operation's name, summary, effect and the tool that runs it |
| `get_operation` | One operation in full: its HTTP route, who may run it (roles, permissions, plan) and the JSON Schema of its arguments |
| `call_read_operation` | Runs an operation that only reads (`readOnlyHint`) |
| `call_write_operation` | Runs one that creates or changes something |
| `call_destructive_operation` | Runs one that deletes, revokes or erases (`destructiveHint`); a client that confirms destructive tools confirms these |

An operation runs only through the tool for its effect. Arguments follow `get_operation`'s schema: path parameters and query fields at the top level, the request body under `body`:

```json
{ "name": "teams.create", "arguments": { "body": { "name": "Support" } } }
```

An operation is the REST route itself, run for you: the same validation, the same role, permission and plan checks, the same audit entry (with `almyty-mcp` as the user agent), and the same error text. Every dedicated tool above also passes its REST route's checks before it runs. The full list of routes, and which tool or operation covers each one, is in `docs/design/almyty-mcp-coverage.md` in the repository.

### Agent runs: tasks, input_required, get_run

`invoke_agent` on an autonomous agent answers by what the request can do (workflow agents still run inside the call):

1. **Tasks extension** (the request's `clientCapabilities.extensions` has `io.modelcontextprotocol/tasks`): `resultType: "task"`, with `taskId` = the run id, `pollIntervalMs` (`MCP_TASK_POLL_INTERVAL_MS`, default 2000) and `ttlMs` (the organization's run retention, `null` without one). `server/discover` lists the extension under `capabilities.extensions`. `tasks/get`, `tasks/update` and `tasks/cancel` need the extension on each request (`-32021` otherwise) and `Mcp-Name` set to the task id.
2. **Elicitation without tasks**: the call waits for the run for up to `MCP_INVOKE_WAIT_MS` (default 25000; `0` turns this off). Finished: the run's result. Stopped for this caller: `resultType: "input_required"` with the question or approval and a sealed `requestState`; the retry with `inputResponses` resumes the run and waits again. Otherwise the run id, as in 3.
3. **Everyone else**: the run id (`runId`) and a pointer to `get_run`. `get_run` reports the status, the output when finished, and `waitingFor` (the question, or the approvals with `youMayDecide`); `answer_run` answers the question. Both need a run of an agent the caller may run.

| Run status | Task status |
| --- | --- |
| `pending`, `running`, `sleeping` | `working` |
| `waiting_input` | `input_required`, one `elicitation/create` keyed `question-<step>` with an `answer` field; `working` with a status message when the client did not declare elicitation |
| `waiting_approval` | `input_required`, one form per pending approval the caller could decide, keyed `approval-<id>` (`decision`, `reason`); otherwise `working` with a status message |
| `completed` | `completed`, `result` = the tool result `invoke_agent` returns (`resultType: "complete"`) |
| `failed`, `timeout` | `completed`, `result` with `isError: true` (a run that failed is a tool error, not a JSON-RPC error) |
| `cancelled` | `cancelled` |

A task is readable, answerable and cancellable only by the user who started it through this server; for anyone else, and for an unknown id, `tasks/get` is `-32602` "Task not found". `tasks/update` ignores keys that are not outstanding (an older question, an approval already decided); a value that is not an elicitation result is `-32602`. `tasks/cancel` cancels the run and acknowledges a run that already ended. Approvals decided here go through the same checks as on the Approvals page, see [Approvals](/approvals).
