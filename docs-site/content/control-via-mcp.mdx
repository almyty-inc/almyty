# Control almyty via MCP

almyty is itself an **MCP server**. Point any MCP client (Claude Code, Cursor, Claude Desktop) at the platform endpoint and your AI assistant can *operate almyty for you*: import APIs, generate tools, build agents, set up gateways, and manage memory, the same actions you'd take in the dashboard, driven from your editor.

This is different from [publishing your own tools on an MCP gateway](/gateways/mcp): there, an LLM calls *your* API tools. Here, the LLM calls *almyty's own management tools* to configure the platform.

## Connect

Add the universal `/mcp` endpoint (the built-in `almyty` system gateway):

```bash
claude mcp add almyty --transport http https://api.almyty.com/mcp
```

Or in a client config file:

```json
{
  "mcpServers": {
    "almyty": { "url": "https://api.almyty.com/mcp" }
  }
}
```

Authenticate once with `npx @almyty/auth login`; the server announces itself as `almyty`.

## What your assistant can do

The control endpoint exposes 69 management tools, grouped by the part of the platform they operate. Every one of them is always available — nothing here is gated behind a plan or a flag.

| Area | What the tools cover |
| --- | --- |
| **APIs** | Connect, update and delete APIs; import a schema and poll the import. `create_api`, `list_apis`, `update_api`, `delete_api`, `import_schema`, `check_import_status` |
| **Tools** | List generated tools, activate one, delete one. `list_tools`, `activate_tool`, `delete_tool` |
| **Tool hub** | Search the ready-made template catalog and install a template as an API plus its tools. `list_tool_templates`, `install_tool_template` |
| **Gateways** | Create and delete gateways, assign tools, add or remove auth. `create_gateway`, `list_gateways`, `delete_gateway`, `assign_tools_to_gateway`, `add_auth_to_gateway`, `remove_auth_from_gateway` |
| **Agents** | Full lifecycle: create, update, activate, deactivate, delete, and run. `create_agent`, `list_agents`, `update_agent`, `activate_agent`, `deactivate_agent`, `delete_agent`, `invoke_agent` |
| **Agent Factory** | Ship an agent as a product: apps, distributions, builds. `list_apps`, `create_app`, `get_app`, `check_app`, `update_app`, `delete_app`, `add_distribution`, `remove_distribution`, `publish_distribution`, `unpublish_distribution`, `build_app`, `list_builds` |
| **Inference providers** | Add and list inference providers. `add_provider`, `list_providers` |
| **Models** | The catalog: models, sync, validation, routing preview, models on your cloud accounts and registered versions. `list_models`, `sync_models`, `validate_model`, `preview_model_routing`, `list_model_deployments`, `list_model_versions` |
| **Connections + credentials** | The one store for third-party secrets: connectors, connections, the connect handshake, grants, and the vault view. `list_connectors`, `list_connections`, `start_connection`, `complete_connection`, `list_connection_grants`, `grant_connection`, `list_credentials` |
| **Memory** | Read, write, search and maintain agent memory across backends. `memory_put`, `memory_get`, `memory_list`, `memory_search`, `memory_delete`, `memory_supersede`, `memory_consolidate`, `memory_sync`, `memory_transfer`, `memory_list_backends`, `memory_backends_health` |
| **Runners** | The daemons that accept dispatched work, and the workspaces open on them. `list_runners` |
| **Organization** | Members and their roles, useful for picking a grant principal or an approver. `list_org_members` |
| **Cost governance** | Spend ceilings and what has actually been spent this period. `list_budgets`, `get_spend` |
| **Analytics** | One organization-scoped report per call: overview, tools, gateways, models, agent runs, alerts, routing failures. `get_analytics` |
| **Approvals** | Pending approval gates, and deciding them so a waiting run resumes. `list_approvals`, `decide_approval` |

## Example

Ask your assistant, in plain language:

```text
> Import the Stripe OpenAPI spec, then publish an MCP gateway with just the refund tools.
```

It chains the management tools: `import_schema`, `check_import_status`, `list_tools`, `create_gateway`, `assign_tools_to_gateway`, `add_auth_to_gateway`, and hands you back a ready endpoint, without you touching the UI.

Or ship an agent as a product, end to end:

```text
> Turn my support-bot agent into an app called Acme Support, set a $2 cost
> cap, add a Slack distribution, and publish it.
```

It chains `create_app`, `update_app` (the limits a public product needs),
`add_distribution`, `check_app`, and `publish_distribution`, and hands you
back a live channel.

## What's not exposed

The control set covers build, configure, and run; a few things stay outside it:

- **No `update_gateway`**: gateways are created and wired here, but editing an existing one is a dashboard or [REST API](/api-reference) job, so a stray model call can't silently rewrite a published endpoint.
- **No direct tool authoring**: tools arrive by importing an API schema or installing a tool-hub template. `activate_tool` and `delete_tool` manage what that produced; there is no `create_tool`.
- **Status is not a settable field**: `create_agent` always produces a DRAFT agent, and `activate_agent` is the only path to active, because it runs pipeline validation first. `invoke_agent` refuses an agent that is not active.
