# MCP tools

MCP (Model Context Protocol) is a common standard AI apps use to call tools. Many services already run an MCP server that offers their actions as tools. Connect one here once and every tool it offers becomes a regular almyty tool: your agents can use it, you can put it in a [gateway](/gateways), and you can try it on its **Test tool** tab.

## Add an MCP server

1. Open **Tools** and click **Add MCP server**.
2. Enter a **Name**. It goes in front of every tool name from this server, so you can tell them apart.
3. Enter the **Server URL**, the address the service gives for its MCP server.
4. If the server needs a key, pick it under **Token or sign-in (optional)** from [Credentials](/credentials), or create one right there. A token is sent as a bearer token (the usual way to pass a key).

   If the server asks you to **sign in** instead (many hosted MCP servers do), sign in once on [Credentials](/credentials): add **MCP server**, open **Advanced**, choose **Sign in to the server**, enter the server's address and click **Sign in**. You approve almyty on the server's own sign-in page and come back. Then pick that sign-in here. almyty renews it before it runs out; if the server ever moves its sign-in somewhere else, the source tells you to sign in again.
5. Click **Add server**. almyty connects, asks the server what tools it has, and adds each one to your tools list with an **MCP** badge. They are active straight away.

The server then appears on **Tools** with its status, its address, how many tools it has and when it last synced.

**Keep it up to date.** Click **Sync** next to the server to pick up tools it added, changed or removed. A tool the server no longer offers is set to inactive rather than deleted, so past runs and gateway settings stay intact. Deleting the server (after a **Delete MCP server?** confirmation) removes its tools too.

If a call fails, the run shows why in plain terms: the server couldn't be reached, it took too long, or it answered with an error.

## For developers

**Protocol.** Streamable HTTP transport; almyty sends protocol version `2025-06-18` and uses the version the server answers with. Both plain-JSON and SSE-framed responses are handled, and the `Mcp-Session-Id` session header is managed for you. Not supported: stdio servers, the legacy HTTP+SSE transport (2024-11-05), and server-initiated requests such as sampling and elicitation. Put those behind a bridge if you need them.

**Discovery and calls.** Adding or syncing runs `initialize` then `tools/list`. When an agent calls a tool, almyty sends `tools/call` with the agent's arguments and returns the result as the tool output.

**Error codes.** Failures come back as typed tool errors on the run: `MCP_CONNECT_FAILED`, `MCP_TIMEOUT`, `MCP_HTTP_ERROR`, `MCP_PROTOCOL_ERROR`, `MCP_REMOTE_ERROR`, `MCP_RESPONSE_TOO_LARGE` and `MCP_URL_BLOCKED`.

**Security.** Server URLs are checked before every request: private ranges, loopback, link-local and cloud-metadata addresses are blocked, and redirects are refused. A self-hosted install that needs in-cluster MCP servers can set `MCP_ALLOW_PRIVATE_URLS=true` (http and https only). The token is a credential kept on Credentials, encrypted at rest; the MCP server entry only points at it.

**Signing in (OAuth).** The **Sign in to the server** way on the `mcp-custom` connector follows MCP authorization:

- *Discovery.* almyty calls the server without a token; its `401` names the Protected Resource Metadata in `WWW-Authenticate` (`resource_metadata`), else almyty tries `/.well-known/oauth-protected-resource` with and without the server's path (RFC 9728). The metadata's `resource` must be the server itself. The first authorization server it lists is read through RFC 8414 metadata, then OpenID Connect discovery; its `issuer` must match, and it must offer PKCE with `S256`.
- *Who almyty is there.* A client id entered under **Advanced** first (with its secret, sent with `client_secret_basic` or `client_secret_post`); else almyty's client metadata document as `client_id`, when the server advertises `client_id_metadata_document_supported` and the API is served over https; else dynamic registration with `application_type: "web"` and `token_endpoint_auth_method: "none"`. The document is served at `GET /credentials/oauth/client-metadata.json` on the API origin (public, no secret, cacheable for `MCP_CLIENT_CIMD_MAX_AGE_SECONDS`); `MCP_CLIENT_CIMD_ENABLED=false` turns it off and `MCP_CLIENT_NAME` sets the name the consent page shows.
- *The sign-in.* PKCE `S256`, and `resource` (RFC 8707, the server's URL) on the authorize and token requests. The scope is the one the `401` named, else every scope the server lists, unless one is entered. The callback is `/credentials/oauth/callback`; its `iss` must be the issuer the sign-in started with (RFC 9207), and is required when the server says it sends it.
- *The tokens.* Kept only on the credential (type `oauth2`), encrypted, with the issuer, resource, token endpoint and client they belong to. They are refreshed `MCP_CLIENT_OAUTH_REFRESH_SKEW_SECONDS` (default 60) before they expire. On a `401` from the server almyty reads its metadata again: if it now names another authorization server, the old token is not sent there and the credential is marked expired with "sign in again" (SEP-2352); otherwise the token is refreshed and the call retried once. A refused refresh marks it expired; an issuer that is down leaves it as it is. Removing the credential revokes both tokens at the issuer's revocation endpoint when it has one (RFC 7009).
- *Limits.* Every discovery, registration and token request goes through the SSRF guard, follows no redirect, times out after `MCP_CLIENT_OAUTH_FETCH_TIMEOUT_MS` (default 10000) and reads at most `MCP_CLIENT_OAUTH_MAX_BYTES` (default 65536). `MCP_ALLOW_PRIVATE_URLS` applies to sign-in as it does to the server.
