# Tools

A **tool** is one thing an assistant can do in one of your systems: "look up an order", "track a shipment", "issue a refund". You don't have to write tools one by one. Connect an API your company already has, and almyty makes a tool for every action it offers.

For example, connecting the Northwind Orders API gives you tools such as *Get an order by number*, *Track the shipment for an order* and *Issue a refund for an order*. An assistant reads each tool's description to decide when to use it.

![Tools list filtered to active tools on the current page, with names, source labels, and status](/screenshots/tools-list.png)

## Two ways to get tools

**Connect an API (the usual way).** Open **APIs** and click **Connect an API**. Pick what kind of API it is (**OpenAPI / Swagger**, **GraphQL**, **SOAP / WSDL**, **gRPC / proto**, **SDK / npm** or **Manual HTTP**), give almyty its description as a link, a file or the text, and click **Connect API**. almyty reads the description and creates one tool per action, with its inputs already filled in. You can also pick one of the **Ready-made provider APIs** (OpenAI, Mistral, Hugging Face Hub), which uses the key you already keep for that provider on **Credentials**.

An API description (sometimes called a schema) is the file that lists everything an API can do. Most APIs publish one; ask whoever runs the system if you can't find it.

| Kind of API | What becomes a tool |
|------|---------------------|
| OpenAPI / Swagger | Each action (an address plus a method) |
| GraphQL | Each query and mutation |
| SOAP / WSDL | Each operation |
| gRPC / proto | Each method |
| SDK / npm | Each function you map |

**Create one by hand.** On **Tools**, click **Create tool**. Pick an **Execution method** (how the tool does its work), give it a **Tool name** and a **Description** (what assistants read to decide when to use it), describe its inputs under **Parameters**, and click **Create tool**.

## Kinds of tool

| Kind | Use it to | Page |
|------|-----------|------|
| HTTP REST API | Call one address of a web API | [HTTP tools](/tools/http-tools) |
| GraphQL | Use the queries and changes of a GraphQL API | [GraphQL tools](/tools/graphql-tools) |
| SOAP | Call an operation of an older SOAP web service | [SOAP tools](/tools/soap-tools) |
| gRPC | Call a method of an internal gRPC service, from its `.proto` | [gRPC tools](/tools/grpc-tools) |
| Custom JavaScript | Run a small piece of code, for a calculation or to reshape data | [JavaScript tools](/tools/javascript-tools) |
| Model prompt | Have an AI model summarize, classify, extract or translate | [LLM tools](/tools/llm-tools) |
| SDK / npm package | Use a function from a JavaScript library | [SDK tools](/tools/sdk-tools) |
| MCP server | Use the tools another MCP server already offers (MCP is a common standard AI apps use to call tools) | [MCP tools](/tools/mcp-tools) |

## Try a tool before anyone uses it

Open a tool and go to **Test tool**. Fill in sample inputs, click **Execute Tool** and see exactly what the system answers. Do this before you hand the tool to an assistant.

![Generated weather tool with its parameter schema and Test tool tab](/screenshots/tool-detail.png)

A tool's page also has **Details**, **Exports** (how to use it through each gateway it is in), **Gateways** (which gateways offer it) and **Stats** (how often it ran and how that went).

## Drafts and active tools

Tools made from an API description start as **drafts**, so nothing is offered until you decide. On **Tools**, click **Select the drafts**, untick any you don't want, and click **Activate selected**. Only active tools are offered to assistants and AI apps.

## What a tool does to your data

Every tool says what calling it does to your data: it **only reads**, it **changes data**, or it **deletes data**. almyty works this out by itself when the tool is made: a tool that looks something up reads, one that creates or updates something changes data, one that removes something deletes data. When nothing about a tool says for sure (code you wrote, a SOAP or gRPC call), it counts as changing data, never as deleting by guess.

You see it on the tool's **Details** tab under **What it does to your data**, with the reason. If almyty got it wrong, pick the right one under **Set it yourself**; **Automatic** goes back to almyty's answer. Your choice stays when the API is imported again.

![The What it does to your data card on a tool's Details tab](/screenshots/tool-side-effect.png)

It matters in two places: AI apps read it as a hint (a tool that deletes data is marked so), and when an agent works through code, calls that delete data wait for a person.

## How assistants find the right tool

With a few tools an assistant can read them all. With hundreds (three imported APIs is often enough) it searches instead: it asks for tools that fit what it is doing ("which pets are sold") and gets the few best matches, each saying what it does to your data, then asks for the full details of the one it picks. almyty matches the words of the request against each tool's name, operation, API, tags, description and parameter values, and, when the organization has connected a model provider that makes embeddings (OpenAI, Mistral or Ollama), also by meaning, so "stock levels" finds a tool called get inventory. A search only ever looks among the tools the assistant may use.

## Give tools to an AI app

Your own almyty [agents](/agents) use tools directly. To offer tools to an outside AI app (Claude Code, Cursor, Claude Desktop), put them in a [gateway](/gateways): one address that offers a set of tools you choose.

## For developers

Serve a gateway's tools to any MCP client from a terminal:

```bash
$ npx @almyty/auth login
$ npx @almyty/mcp-server acme/petstore
```

See the [MCP server CLI](/cli/mcp-server) for client configuration.


**Side-effect class.** Every tool has `sideEffect` (`read`, `write`, `destructive`), `openWorld` (it reaches a third party; `false` for LLM tools) and `sideEffectSource`, computed whenever the tool is written:

| `sideEffectSource` | Rule |
| --- | --- |
| `override` | Set with `PUT /organizations/:organizationId/tools/:toolId` and `{"sideEffect": "read" \| "write" \| "destructive"}`; `"auto"` drops it. Survives re-import; audited. |
| `annotation` | A tool from an MCP source: `readOnlyHint: true` reads, `destructiveHint: true` deletes, otherwise write; `openWorldHint` is copied. |
| `http_method` | `GET`, `HEAD`, `OPTIONS` read; `DELETE` is destructive; `POST`, `PUT`, `PATCH` write. Generated tools and hand-made HTTP tools with a literal method. |
| `graphql` | A query or subscription reads, a mutation writes. |
| `default` | An LLM tool reads; anything else with no reliable signal (JavaScript, SOAP, gRPC, SDK, a templated HTTP method) is `write`. |

The class is part of the tool's integrity hash: a tool whose stored class was changed outside its own update path fails verification and does not run. MCP gateways emit it as `readOnlyHint`, `destructiveHint` and `openWorldHint` (see [MCP gateway](/gateways/mcp)).
**Statuses.** A tool's `status` is `draft`, `active`, `inactive`, `deprecated` or `deleted`. Gateways serve only `active` tools.

**Exports.** Besides the per-gateway instructions on the **Exports** tab, the API exports any tool as a SKILL.md file (`GET /organizations/:organizationId/tools/:toolId/skill`), a command-line script (`GET /organizations/:organizationId/tools/:toolId/cli?format=bash` or `format=node`) and generated client code (`GET /organizations/:organizationId/tools/:toolId/sdk`). See the [Tools API](/api-reference/tools-api).

**Search and signatures.** `POST /organizations/:organizationId/tools/search` with `{"query": "...", "limit": 10}` ranks the active tools the caller can see and returns `[{ name, summary, sideEffect, score }]`. `GET /organizations/:organizationId/tools/:toolId/signature` returns a tool's full description: `inputSchema`, `outputSchema` when known, `sideEffect`, its code name (`{ namespace, function }`: the API's name and the operation id, `custom` for a hand-made tool) and TypeScript signature as a script calls it, and one example call. On an MCP gateway, `tools/search` and `tools/get` answer the same way over exactly the gateway's `tools/list` set (and keep their earlier response fields); a tool the gateway does not serve is `-32602`.

Ranking is reciprocal rank fusion of a keyword ranking (name 4, operation id and API name 2, tags 2, description 1, parameter names and enum values 1; a word's start counts fully, anywhere inside a field half; common English words are ignored) and an embedding ranking (cosine distance, only between vectors of the same model). Tools are embedded by a background job whenever they are written; a search that finds tools without a vector of the current model queues them. Without an embedding provider the hash fallback embeds, and its ranking counts a quarter (`TOOL_SEARCH_FALLBACK_VECTOR_WEIGHT`). Settings: `TOOL_SEARCH_DEFAULT_LIMIT` (10), `TOOL_SEARCH_MAX_LIMIT` (50), `TOOL_SEARCH_RRF_K` (60), `TOOL_SEARCH_VECTOR_CANDIDATES` (100), `TOOL_EMBEDDINGS_ENABLED` (true), `TOOL_SCOPE_MAX_TOOLS` (5000).
