# Gateways

Publish your tools once, reach them from any agent or client. A gateway takes the
tools you have already built and exposes them from one authenticated address that
speaks MCP, UTCP and Agent Skills; an A2A gateway serves an agent. You pick which tools
a gateway serves, so every address has a focused, purpose-built surface.

![A gateway detail page with its assigned tools, endpoint, and auth](/screenshots/gateway-detail-tools.png)

## The payoff

Scope a gateway to the tools you want, generate a key in its Authentication section, then
add it to Claude Code in one line:

```bash
claude mcp add petstore --transport http https://api.almyty.com/acme/petstore
# clients send: x-api-key: <your gateway key>
```

```text
> look up pet #2 and show its status
  Claude calls getPetById via almyty -> "Rosie", available
```

The same address answers MCP, UTCP and Agent Skills, so other frameworks and coding
agents reach the identical tools without a second gateway. A2A is the agent-facing
counterpart: it serves one of your agents rather than a set of tools. Web chats and
messaging channels are places on an app, set up under **Apps**.

## Share tools

1. Open **Gateways** in the sidebar and click **Share tools** to open `/gateways/new`
2. Under **What to share**, pick a whole API or single tools (a draft can't be shared until it is active)
3. Name it; the address follows from the name, and **Advanced** changes the path and who can use it
4. Click **Share**, then copy the access key: it is shown once
5. Change which tools it serves from **Tool scoping** on the gateway page, and its auth from the **Authentication** section

The gateway's **Integrations** tab gives you the live endpoint plus discovery URLs to
paste into any client:

![A gateway's MCP endpoint, SSE, and discovery URLs](/screenshots/gateway-petstore-integration.png)

## Protocols

One set of tools, four ways to reach them. Every gateway is served from the same
`api.almyty.com/{org}/{gateway}` URL — there is no per-protocol path segment. Which
protocol answers there is fixed by the gateway's type, chosen when you create it, so
start with the protocol your client speaks and give that gateway its own slug:

| Protocol | Reach it with | Endpoint |
|----------|---------------|----------|
| [MCP](/gateways/mcp) | Claude, Cursor, Windsurf, VS Code Copilot | `api.almyty.com/{org}/{gateway}` |
| [A2A](/gateways/a2a) | Google A2A agents, via the Agent Card | `api.almyty.com/{org}/{gateway}` |
| [UTCP](/gateways/utcp) | Any HTTP client or agent framework | `api.almyty.com/{org}/{gateway}` |
| [Agent Skills](/gateways/skills) | 30+ coding agents, via the Skills CLI | Installed as `SKILL.md` files |

Agents you build on almyty also get an [OpenAI-compatible endpoint](/api-reference/openai-compatible),
so anything that talks to the OpenAI API can call an agent without code changes.

## Control what each gateway exposes

- **[Authentication](/gateways/authentication)**: default-deny on every gateway. Add API
  key, bearer, basic, JWT, OAuth 2.1, and manage keys per client.
- **[Tool scoping](/gateways/tool-scoping)**: choose exactly which tools a gateway serves,
  with per-gateway rate limits and security policies on each tool.
