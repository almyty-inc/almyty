# Tool Scoping

Decide exactly which tools each gateway exposes. A gateway starts empty and you assign tools into it, so every gateway has a focused, purpose-built surface: a read-only public one, a full-access internal one, one per team. Nothing is exposed until you choose it.

![Assigning tools on the gateway Tool scoping tab](/screenshots/gateway-detail-tools.png)

## Assign tools in the UI

1. Open the gateway detail page and click the **Tool scoping** tab.
2. Search the available tools, grouped by API, and click **Assign** beside a tool. Inactive tools must be activated on the Tools page first.
3. Use an API group's checkbox or the preset buttons for bulk assignment (see below).
4. Click **Remove** to stop exposing an assigned tool.
5. Use an assigned tool's shield button to expand its inline **Security policy** form.

Only tools accessible to the gateway can be assigned; Private tools are not available for public gateway exposure.

## Presets

| Preset | Description |
|--------|-------------|
| **All tools** | Assign every available tool |
| **Remove all** | Remove all assignments |
| **Read only** | Assign only GET/query operations |
| **Admin tools** | Assign all CRUD operations |
| **Public API** | Assign tools suitable for public access |

## Per-gateway tool configuration

Each assignment can carry gateway-specific overrides. Edit the security policy from the **Tool scoping** tab; use the API for other assignment fields such as `rateLimit`. The stored config looks like this:

```json
{
  "enabled": true,
  "rateLimit": 100,
  "securityPolicy": {
    "requireAuth": true,
    "allowedScopes": ["tools:execute"]
  }
}
```

| Field | Type | Description |
|-------|------|-------------|
| `enabled` | boolean | Whether the tool is active on this gateway |
| `rateLimit` | number | Max requests per minute for this tool |
| `securityPolicy` | object | Gateway-specific security overrides |

The same tool can be read-only on a public gateway and rate-limited differently on an internal one. Overrides live on the assignment, not the tool itself.

## Usage statistics

Each gateway tracks per-tool usage so you can see what is actually being called. The stats include call counts, success rate, and latency:

```json
{
  "stats": [
    {
      "toolId": "tool-1",
      "toolName": "get_users",
      "totalCalls": 1250,
      "successRate": 98.4,
      "avgDuration": 234,
      "lastCalledAt": "2026-03-23T10:30:00Z"
    }
  ]
}
```

## Common patterns

**Read-only public gateway:** assign only GET/query tools, enable API key auth, set per-tool rate limits.

**Internal admin gateway:** assign all tools, require Bearer token auth, no rate limits.

**Per-team gateways:** create separate gateways per team (marketing gets analytics tools, engineering gets deployment tools), each with its own keys and scopes.

See [Gateway Authentication](/gateways/authentication) for the auth and scope options referenced above.
