# Runners

A runner is a small daemon you start on a machine (your laptop, a cloud VM, a
Kubernetes pod, a Docker container, an edge device) anywhere Node runs. It
connects that machine to almyty and exposes it to your agents: they run commands
and use the local tools and files there. almyty's own model calls go through the
backend; coding CLIs started on the runner call their providers directly. Tool
results return to the calling agent, so local execution is not a promise that
file contents or secrets cannot leave the machine.

![A runner's detail page: detected binaries and the Coding agents card](/screenshots/runner-detail.png)

## Start a runner

The easiest way is the **Runners → Start a runner** page: keep or change the
suggested name, add optional labels (short tags such as `os=mac` that say what
the machine has, see [below](#send-work-to-a-matching-machine)), and pick who can see it (**Private** is the default, then **Team** or
**Org-wide**). The page creates the runner and prints the commands below with
your name filled in. You can go back and change anything, or cancel, which
deletes the runner again.

On the machine, install once and call the installed binaries:

```bash
npm i -g @almyty/runner @almyty/auth
almyty-auth login
almyty-runner start --name my-laptop --org <org-id>
almyty-runner status
```

It appears in the **Runners** page as online. Stop it with `almyty-runner stop`
or Ctrl-C in its terminal.

**What identifies and authorises the runner is your almyty login on that
machine, not its name.** The daemon connects with the token `almyty-auth login`
stored, and the backend attaches it to that user's runner. Names are unique in
an organization, so someone who knows yours gets refused rather than connected,
and another member cannot attach a session to your runner by its id either.

**Visibility** decides who else can use it. A private runner is listed, fetched
and dispatched to for its owner only (org admins included); its published tools
are private too. Team and Org-wide open it to a team or to every member.

v1 attaches **one runner per account**. Multi-machine
registration is not available yet.

## What an agent can do on it

The runner exposes a generic process surface (spawn, shell, read, write,
signal) scoped to a [workspace](#workspaces). So an agent can do whatever the
machine can: run a build, query data that only lives there, operate a server, or
drive a CLI it detects. The orchestration lives in the agent's prompts; the
runner just runs the processes.

Its capabilities (such as `shell.exec` and `runner.info`) are published as tools,
tagged with the runner's name. Attach them to a [gateway](/gateways) and any
agent can call them: one you built, or a Claude Code session over MCP.

## Send work to a matching machine

Labels say what a machine has, such as `os=mac` or `gpu=yes`. Work that asks
for labels runs only on an online runner that carries all of them:

- **An agent**: on its edit page, under **Capabilities > Machine**, fill
  **Machine labels** (for example `gpu=yes, os=mac`). The page lists the
  machines that carry them. Every runner tool the agent calls then runs on a
  matching online runner, the tool's own runner when it matches.
- **A workspace**: one created with `labels` is placed on a matching online
  runner. Work inside a workspace always stays on that workspace's runner.

Only runners the work may use count: a private runner takes its owner's work,
a team runner its team's. When nothing matches, the call fails with a plain
message, for example `No machine with gpu=yes is online`. Labels compare
without regard to case, and a runner may carry more labels than the work asks
for.

## Coding agents

The runner natively drives the major coding-agent CLIs: Claude Code, Codex,
Gemini, Cursor, aider, and more. It detects which are installed at startup
(shown in the **Coding agents** card above) and can launch them as unattended
members: it injects the provider key for headless auth, isolates each one's
config and session, enables auto-approve, and reports live status
(busy / idle / awaiting input). That is the building block for a multi-vendor
coding team, one agent driving several CLIs on the same codebase. You compose
the orchestration; the runner runs the members.

## Workspaces

Work happens inside a **workspace**: a folder on the runner reserved for a limited
time. Agents get them automatically. When an agent run calls a runner tool that
works inside a workspace (such as `shell.exec`) and none is bound, almyty asks
the runner to make a folder, records a workspace for it and runs the call there.
The rest of that run reuses the same workspace on that runner; another run gets
its own.

- **One job, one folder.** Helper agents and sub-agents that a run starts work
  in that run's workspace when they use the same runner. A sub-agent sent to a
  different runner gets its own workspace there, still counted as part of the
  same job.
- **The folder** is named after the agent and the run (`support-bot-1a2b3c4d`).
  It goes in `~/.almyty/workspaces/` on the runner, or in `almyty-workspaces/`
  under the first of the runner's `allowedCwdRoots` when those are set.
  Releasing or expiring the workspace stops its processes; the folder and its
  files stay on the machine.
- **When the run ends** (it completes, fails, is cancelled or times out), its
  workspaces are released right away, which frees the runner for other work.
  The one-hour limit stays as a safety net.
- **Whose it is**: the user who started the run, or the owner of the private or
  team gateway the run came through. A run through an org-wide gateway has no
  one to hold a workspace, and its call fails saying so.
- **Time limit**: one hour. After a workspace is released or expires while the
  run is still going, the run's next call gets a new one in the same folder. If
  the runner goes offline, its workspaces are stranded.
- **Capacity**: a runner holds at most its `maxConcurrent` active workspaces.
  Past that, or when the runner cannot make the folder (outside its
  `allowedCwdRoots`, or a runner too old to make folders), the tool call fails
  with a message that says why, and the agent sees that error.

Each runner's page has a **Workspaces** tab (`/runners/:id?tab=workspaces`)
listing the workspaces on that runner, active ones first, with the folder, the
agent and run it was made for, status, isolation and time left, and a
**Release** button on each active one. Who sees which:

- Everyone sees their own workspaces.
- The runner's owner sees every workspace on their runner, including ones other
  members' agent runs were given, and can release them.
- Organization owners and admins see and can release every workspace on team
  and org-wide runners. A private runner's workspaces are its owner's only.

Anyone else asking for a workspace, on the page or through the API, is told it
was not found. A row opens the workspace's own page under the runner. There is
no create button. A script can still make one through the API: `POST
/workspaces` with the folder (`cwd`) and the runner (`runnerId`, or `labels` to
let almyty pick a matching runner). Such a workspace is passed to a tool call
as `workspaceId`. The current runner uses host execution, not a filesystem or
network sandbox: a workspace does not prevent a command from accessing other
files the daemon's operating-system user can read. Set local path and command
restrictions and review the [runner safety limits](/cli/runner#what-a-runner-can-do-on-your-machine).

## Notes

- **One runner per account** in v1.0: starting a second one under another name is refused until you delete the first.
- **Where LLM calls happen.** almyty's own agents run their LLM calls through the
  backend, not the runner. The runner just executes local processes. The
  exception is the coding-agent CLIs you spawn on the runner: they authenticate
  to their provider directly with a key you supply, so those calls leave from the
  machine itself.
