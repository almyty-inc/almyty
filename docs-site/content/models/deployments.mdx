# Deployments

Run a model wherever it already lives: weights you point at, or a model a platform already hosts and versions itself. Name the model as a string, pick an adapter, and the reconcile loop makes it real. When the endpoint is ready it becomes a [model card](/models) with a privacy tier, a region and a price, and the [router](/models/routing) picks it like any vendor model. Scale it to zero, cap what it may spend, tear it down.

Registering a version first is optional. Do it when you want lineage, a manifest digest and evaluation history tied to your own artifact; skip it and deploy straight from a `model` string when you just want to run something that already exists somewhere.

```
Model reference                    Deployment                        Catalog
hf://Qwen/Qwen3-14B@e3b0    ->      adapter + config + desired  ->    card (endpoint, tier, price)
bedrock://anthropic.claude...       reconcile every 2 min              router picks it
```

The whole flow from the terminal, deploying straight from a Hugging Face repository:

```bash
$ npx @almyty/models deploy hf://Qwen/Qwen3-14B@e3b0c442 --adapter huggingface-endpoints \
    --config '{"token":"hf_...","namespace":"acme","region":"eu-west-1","instanceType":"nvidia-a10g"}' \
    --desired '{"replicas":1,"privacyTier":"private_cloud","region":"eu-west-1"}'
Queued.
c07b...  huggingface-endpoints  pending  replicas ?/1
$ npx @almyty/models deployments --json | jq -r '.[0].actual.url'
https://acme-qwen3-14b.eu-west-1.aws.endpoints.huggingface.cloud/v1
$ npx @almyty/models register-endpoint --name "Support fine-tune" --url https://acme-qwen3-14b.eu-west-1.aws.endpoints.huggingface.cloud/v1 \
    --model qwen3-14b-support-ft --tier private_cloud --region eu-west-1
$ npx @almyty/models validate 4f2a...
Passed in 1210 ms.
```

A model already on a platform deploys the same way, with a provider reference instead of an artifact:

```bash
$ npx @almyty/models deploy fireworks://accounts/acme/models/qwen3-tuned --adapter fireworks --card 4f2a...
```

## The registry

almyty is not in the hosting business: no adapter provisions a machine, and weight bytes never pass through this backend. Most deployments never need a bucket at all. The registry, your organization's own S3-compatible connection (AWS S3, MinIO, Cloudflare R2, DigitalOcean Spaces, connected under [Connections](/connections)), matters only to the adapters whose provider reads object storage directly with its own role or keys: `aws-bedrock-import`, `sagemaker`, `fireworks`, `baseten`, and a self-hosted `custom-endpoint` pointed at a server that reads its own store. Everyone else names a Hugging Face repository, a provider's own catalog entry, or a model already uploaded to the platform, and none of those need a bucket connected at all.

Deploying a registered `s3://` version when the organization has no registry connection is refused: `REGISTRY_NOT_CONNECTED`.

A single-tenant self-host can seed the one organization's connection from `MODEL_REGISTRY_S3_*` (falling back to `STORAGE_S3_*`) on first boot. With two or more organizations those variables are ignored.

### URIs

A model reference is one of two kinds.

**Artifacts** point at bytes and must be pinned, because a version has to be immutable:

| Shape | Meaning |
|---|---|
| `hf://org/repo@sha` | A Hugging Face repository, the native default for most providers |
| `s3://bucket/prefix@etag` | Your own S3-compatible bucket, read directly by the adapters that support it |
| `gs://bucket/prefix@generation` | Google Cloud Storage, Vertex's own native source |
| `file:///abs/path@sha` | A path on a runner or an Ollama host |

**Provider references** name a model that already exists on a platform. The platform owns the versioning, so no pin is required:

| Shape | Runs on |
|---|---|
| `bedrock://<model id or arn>` | `aws-bedrock-import` |
| `sagemaker://model-package/<arn>` | `sagemaker` |
| `vertex://publishers/<publisher>/models/<model>` | `vertex` |
| `foundry://<format>/<name>@<version>` or `azureml://registries/<registry>/models/<name>/labels/<label>` | `azure-foundry` |
| `fireworks://accounts/<account>/models/<model>` | `fireworks` |
| `together://<owner>/<model>` | `together` |
| `baseten://<model id>` | `baseten` |

A reference that doesn't match what the chosen adapter reads is refused at submit with `ADAPTER_UNSUPPORTED_SOURCE`, not discovered as a provider error later.

### Layout and manifest

For a registered `s3://` version:

```
<prefix>/
  almyty-manifest.json
  model.safetensors            (or sharded model-00001-of-0000N.safetensors)
  tokenizer files as referenced by the manifest
```

Weights are plain safetensors. Nothing about where the model will run is stored here.

```json
{
  "schemaVersion": 1,
  "base": "qwen3-14b",
  "tokenizer": "s3://acme-models/qwen3-14b-support@e3b0c442/tokenizer",
  "chatTemplate": "chatml",
  "license": "Apache-2.0",
  "created": "2026-09-08T09:00:00Z",
  "files": [{ "path": "model.safetensors", "sizeBytes": 29000000000, "sha256": "..." }],
  "quantizations": ["bf16", "awq-int4"],
  "lineage": { "parentVersionId": "..." }
}
```

Required: `schemaVersion` (1), `base`, `tokenizer`, `license`, `created` and at least one entry in `files` with relative paths. The manifest's canonical SHA-256 is recorded on the version as `manifestSha`; the sum of `files[].sizeBytes` becomes `sizeBytes`.

## Versions

Registering a version is optional, and exists for operators who want lineage, a manifest digest and evaluation history tied to their own artifact. Registering an `s3://` version reads and validates the manifest at the URI and fills base, size, digest and quantizations from it; an unreadable manifest is an error. For every other scheme the manifest is optional: when absent, `base` must be given.

A version cannot be deleted while a deployment that is not torn down references it (`VERSION_IN_USE`). The platform never deletes weights on its own: deployments come and go, versions stay.

## Adapters are data

An adapter is the code that talks to one provider. Everything a form or a script needs to use it is served as data by `GET /model-adapters`, so shipping a new adapter changes no UI:

| Field | Meaning |
|---|---|
| `key`, `displayName` | The adapter id you pass as `providerType`, and its label |
| `capabilities.architectures` | Model families it accepts, or `any` |
| `capabilities.lora` | `merged`, `multi` or `none` |
| `capabilities.serverless`, `capabilities.dedicated` | Whether it runs without a dedicated instance, on one, or either |
| `capabilities.scaleToZero` | Whether replicas 0 stops the bill |
| `capabilities.regions` | Regions the provider offers; empty means the provider chooses or the list is dynamic |
| `capabilities.registrySources` | Which artifact schemes it reads, in any combination of `hub`, `s3`, `gcs`, `local` |
| `modelSchemes` | Every reference this adapter actually accepts, artifact and provider reference alike, as literal prefixes (`hf://`, `s3://`, `bedrock://`, ...). What a form filters on in both directions: the providers that can run the model you have, and the sources the provider you picked will take |
| `configSchema` | A JSON schema for the adapter's `providerConfig`. Properties marked `"x-secret": true` are encrypted at rest and never returned |

A source or an architecture the adapter can't take is refused when the deployment is submitted, not discovered as a provider error later. The unsupported-source error is `ADAPTER_UNSUPPORTED_SOURCE`, and it carries `accepts`, the list of schemes the adapter does take.

Adapters never import each other, and every one passes the same conformance suite in fixture mode: deploy against a recorded HTTP surface, poll to ready, chat through it, scale to zero, tear down, and report a sane cost, plus the failure cases (unsupported source, unsupported architecture, quota, expired credential, orphan). None of that is specific to any one source.

**Every adapter below is fixture-only.** None has ever been run against a real provider account. `CONFORMANCE_LIVE=<adapter key>` mode drives the same suite against the real provider with real credentials, but it has never executed: it needs credentials nobody holds yet, and it never runs in CI. Read every claim in this page as verified against the provider's own documentation, not against a live account.

## Desired and actual

A deployment is desired state. `POST /model-deployments` records what you want; the reconcile sweep (`MODEL_RECONCILE_CRON`, every two minutes by default, plus an immediate run after each change) is the only thing that talks to the provider.

| Field | Meaning |
|---|---|
| `model` | The model to run, as a string: `hf://org/repo@sha`, a provider reference such as `bedrock://...`, or any other scheme the chosen adapter reads |
| `modelVersionId` | A registered version instead of `model`, for lineage |
| `base` | Architecture family, when the adapter checks it and the reference itself doesn't carry one |
| `providerType` | The adapter key |
| `desired` | `hardware`, `replicas`, `minScale`, `maxScale`, `quantization`, `region`, `privacyTier` |
| `providerConfig` | The adapter's config, validated against its schema; secrets encrypted in place |
| `credentialId` | A stored credential whose fields the adapter reads; inline secrets in `providerConfig` are layered over it |
| `budgetId` | A [spend budget](/cost-governance); reaching it scales the deployment to zero |
| `modelId` | A card that already exists for this model; the deployment fills its endpoint once ready and keeps pricing it |

Exactly one of `model` or `modelVersionId` is required. Naming neither is `MODEL_REQUIRED`.

Registry keys are never part of `providerConfig`. For the adapters that read your bucket directly (`aws-bedrock-import`, `sagemaker`, `fireworks`, `baseten`), deploying a registered `s3://` version hands the adapter your registry connection per call; the adapter never stores them.

Each tick reads the endpoint, compares it with the desired state, acts (deploy, scale, tear down) or marks the row `degraded`, writes what it saw into `actual` (state, URL, replicas, hardware, region, a message), records the cost snapshot, and writes an audit event with the adapter key and the transition. The deployment moves through `pending`, `deploying`, `ready`, `degraded`, `scaling`, `tearing_down`, `torn_down`, `failed` or `orphaned`. `lastError` carries the provider's last message.

`POST /model-deployments/:id/scale { replicas }` and `POST /model-deployments/:id/teardown` change desired state only; `DELETE` is the same as teardown. Reading a deployment back shows every secret in `providerConfig` as `********`.

When a deployment reaches `ready`, the card named by `modelId` gets `endpointRef.url` and `endpointRef.deploymentId`, becomes `active`, and takes the region the provider reports (or the desired one). Where the provider reports a per-token price, the card is priced from the cost snapshot (`pricingSource: adapter`) unless an override is set. A deployment without `modelId` has no card yet: register its `actual.url` with `register-endpoint` (a card registered against an endpoint defaults to the `private_cloud` tier), then validate it. Either way, validate the card and it is selectable.

## Budgets and scale to zero

A deployment with a `budgetId` is charged from the adapter's cost snapshot on every reconcile: spend so far, the current burn rate in cents per hour, and a per-token price where the provider has one. Reaching the budget sets desired replicas to 0, scales the endpoint down, writes a `model_deployment_budget_stop` audit entry with the amount and the limit, and sends a `model.deployment.budget_stop` notification. It does not repeat on later ticks.

What "scale to zero" costs depends on the provider, and each adapter's `scaleToZero` capability says whether replicas 0 stops the bill. Where it does not (DigitalOcean's Dedicated Inference bills for the accelerators it holds until torn down; Vertex's v1 API keeps at least one replica), the section below says what replicas 0 does instead and what still bills. Most providers publish no billing API, so spend is usually the configured hourly rate times observed running time, marked as an estimate.

## Orphans

A deployment the provider no longer knows (the endpoint was deleted from the vendor console, or the account went away) is reported `missing` by the adapter. A row that is still `deploying` gets 30 minutes of grace; past that, or in any other state, the row is marked `orphaned`, anything left at the provider is torn down, and a `model_deployment_orphan_teardown` audit entry is written. Weights are never touched.

## Adapters

What differs between adapters is the account you need, which model references it reads, what replicas 0 means there, and how spend is measured. Every one of them is fixture-only; see the honesty note above.

### huggingface-endpoints

Hugging Face Inference Endpoints, the only dedicated product Hugging Face runs for you (their serverless offer, Inference Providers, routes to a third party and deploys nothing of yours, so it is call-only, not this adapter). Needs a Hugging Face token with the Inference Endpoints write scope and your namespace (user or organization); choose the vendor (`aws`, `gcp`, `azure`), region, accelerator, instance type and size, and the endpoint type (`public`, `authenticated` or `private`). Source: `hub` only. There is no field anywhere in the create body for object storage, a URL or an upload, so an `s3://` version is refused with `ADAPTER_UNSUPPORTED_SOURCE`. Deploy sends the Hub `repository` and, when the version pins one, `revision`; a gated or third-party repo's token goes in the container secret `HF_TOKEN`, held by Hugging Face, not by us. Regions as read on 2026-09-09: aws `eu-west-1`, `us-east-1`, `us-east-2`, `us-west-2`; azure `eastus`; gcp `us-east4`. Replicas 0 calls the endpoint's scale-to-zero (nothing billed, resumed on the next positive count); the endpoint also scales to zero on its own after its configured idle timeout. Cost is `hourlyRateCents` times running time, priced from Hugging Face's public `GET /v2/provider` list, since there is no usage API.

### modal

Modal Endpoints, the managed product: Modal builds, runs and autoscales the serving stack. A model of ours always deploys as a Dedicated Endpoint (Shared Endpoints only serve Modal's own catalog). Needs a Modal token id and secret (`MODAL_TOKEN_ID` / `MODAL_TOKEN_SECRET`) in the child process environment, never on a command line, and your workspace slug. Source: `hub` only: `--model` is a required Hugging Face repo id. Fine-tuned weights layer on top with `--custom-hf-repo` or `--custom-volume-name` (a Modal Volume the operator already filled themselves; almyty never writes one). There is no HTTP control plane: the adapter shells out to the `modal` CLI, which must be on the API image's PATH. Deploy runs `modal endpoint create --model <hf repo>`; Modal has no replica flag, since capacity is its own job, so `scale` only records intent and a ceiling of 0 is reported `stopped` at no cost. Teardown runs `modal endpoint stop`. Cost is `hourlyRateCents` times observed running time; Modal's billing API is gated to Team and Enterprise plans and not per-endpoint, so it is not wired.

### ollama

Any Ollama server: your own laptop, or a box you rent and run yourself. There is no managed product here and almyty never provisions the machine, installs Ollama, or moves weights; it talks to a server that already exists at a URL you give it. Needs the server URL and, only behind a reverse proxy that checks one, a bearer token. Sources: `hub` (pulled by Ollama itself as `hf.co/org/repo[:quant]`) and `local` (a GGUF file or a directory of safetensors already on the server's own filesystem, or a library tag such as `qwen3:8b`). Ollama has no object-storage client: an `s3://` version is refused with `ADAPTER_UNSUPPORTED_SOURCE`, including when a mirror directory is configured, because mirroring a bucket onto the host would make almyty the delivery route for the weights. Deploy pulls the Hub repo or creates the model from a host path, then loads it into memory when `replicas > 0`; residency in VRAM is the closest thing Ollama has to a replica count, so `scale(2)` is `scale(1)`. Scale to zero unloads with `keep_alive: 0`; a positive count reloads. Ollama bills nothing itself; set `hourlyRateCents` to account for a rented box, and it drops to zero while the model is unloaded. A private URL needs `OLLAMA_ALLOW_PRIVATE_URLS=true` on a self-hosted API.

### custom-endpoint

An OpenAI-compatible server somebody else already runs (vLLM, TGI, llama.cpp, SGLang, a LiteLLM proxy, a vendor's private endpoint). There is no product here either: almyty does not create it, scale it or delete it. It watches it, prices it, and lets the router pick it like any other card; `deploy`, `scale` and `teardown` all refuse. `registrySources` is `hub, local`, the two honest answers to where the weights came from for a self-run server; nothing in the adapter actually reads a source. Config: the base URL, an optional key, the model id sent on the wire, and either per-token prices or an hourly rate. Registering one goes through `register-endpoint` on the [Providers](/models/providers#any-other-openai-compatible-server) page, not through this adapter's deploy path. `readEndpoint` reads `GET /models`; an unreachable host reports `degraded` rather than `failed`, since a self-run box coming back is normal.

### baseten

Baseten dedicated deployments through the BIS-LLM engine, config-only against a prebuilt serving image. Needs a Baseten API key; choose the accelerator, the engine backend (`vllm` or `trtllm`), the scale-down delay and the concurrency target. Sources: `hub`, `s3` and `gcs`: the Baseten Delivery Network mirrors weights from all three itself (also `bt://`, `r2://`, `cw://` and `azure://`, which the adapter accepts too but has no capability flag for). A private or gated source is authenticated by a per-source `auth` block, not by the top-level secrets config: for Hugging Face the secret is named `hf_access_token`; for S3 it is `aws_credentials` holding `aws_access_key_id`, `aws_secret_access_key`, `aws_region` under those exact key names. The secret is workspace-wide, upserted on every deploy and never deleted on teardown. `regions` is empty in `capabilities()`: placement is enabled per workspace by Baseten and listed by `GET /v1/regions`. Scale to zero calls `deactivate`, immediate and free; a positive count PATCHes the replica bounds and calls `activate`. Cost comes from Baseten's billing summary (a per-deployment breakdown, up to 31 days) and its instance price list, falling back to `hourlyRateCents` times uptime when the key lacks billing scope.

### together

Together dedicated model inference (DMI), a v2 resource model; v1 is closed to new endpoints entirely. Needs a Together API key scoped to one project. Choose the instance type from Together's published catalog, autoscaling bounds and windows, and placement (set once, at create time only; Together cannot move a live deployment). Source: `hub` only. An upload registers the version as a project model against `providerConfig.baseModelId` (required, and not guessable from a reference), then POSTs a remote upload naming the Hub URL and, for a private or gated repo, your own Hub token; Together streams the weights server-side. The result is a `together://ml_...` reference that later deploys of the same model reuse. Routing is a separate, non-optional step on this product: a deployment can read `READY` and still receive no traffic, so deploy also PATCHes the endpoint's traffic split once the deployment is up. When a model publishes more than one deployment profile the adapter refuses and lists them; `providerConfig.configId` picks one. Scale to zero sets both replica bounds to zero; a positive count raises the floor. Teardown clears the split, stops the deployment, deletes it, then deletes the endpoint. Cost is the published per-replica instance price times uptime; Together's usage API reports request and latency metrics but no dollars.

### fireworks

Fireworks on-demand deployments: dedicated GPUs for a model that is already a Fireworks resource. Needs a Fireworks API key and your account id; choose a `deploymentShape` (Fireworks now warns that most failed creates are unshaped deployments) or an explicit accelerator and count, plus precision, placement (`GLOBAL`, `US`, `EUROPE`, `APAC`, or one of 26 single regions; new accounts have quota in `GLOBAL` only, and single-region placement costs 1.5x) and the scale-to-zero window. Source: `s3` only, and the import is the operator's own step: Fireworks reads a bucket itself, with a role ARN or keys you give it, run through `firectl model create <MODEL_ID> s3://bucket/path/ --role-arn ...`. There is no REST field for that import, so for an `s3://` version the adapter looks up the resulting model in your account and, when it is missing, refuses with `ADAPTER_UNSUPPORTED_SOURCE` and the exact `firectl` command to run. A `hub` version cannot be served at all: the Hugging Face URL field on a Fireworks model is training metadata, not an import source, and is refused up front. Scale to zero sets the replica floor to zero; a scaled-to-zero deployment answers 503 while it wakes, and Fireworks deletes a zero-floor deployment with no traffic after seven days. Cost comes from metered `accelerator_seconds` (Fireworks' own usage API) priced at the published per-GPU-hour rate, times 1.5 for single-region placement.

### aws-bedrock-import

Amazon Bedrock, in your own AWS account, over two routes chosen by the reference. `bedrock://<model id or arn>` takes Bedrock's own catalog: one application inference profile, created and billed per token by AWS, with no import and no role needed. `s3://` takes Custom Model Import: your own weights, read by AWS directly through an import role ARN; no registry access keys are ever handed to AWS. Needs an access key pair (or temporary credentials with a session token) and the region (`us-east-1`, `us-east-2`, `us-west-2`, `eu-central-1` only for the import route); the import route also needs the role ARN. Import architectures are gated by prefix of the version's base (Mistral, Mixtral, Flan, Llama 2/3/3.1/3.2/3.3, Mllama, GPTBigCode, Qwen2/2.5, Qwen3, GPT-OSS); weights must be Hugging Face format under 200 GB (100 GB multimodal). Bedrock is serverless on both routes: on the catalog route `scale()` sends nothing, since AWS decides capacity and bills per token; on the import route `scale(n)` records a ceiling only and `scale(0)` marks the model standby at zero rate. There is no cancel API for an import job, so teardown deletes the imported model once the job has finished. Cost is exact per-token pricing on the catalog route (`spentCents: 0`, the operator's rates as `perToken`) and an estimate (custom model units per copy times the per-unit rate, times hours since import) on the import route.

### sagemaker

Amazon SageMaker AI real-time inference, in your own AWS account. Needs an access key pair (or temporary credentials) and an execution role ARN that can pull the serving image and read the registry bucket. Source: `s3` only, plus the provider reference `sagemaker://model-package/<arn>` for a JumpStart or AWS Marketplace model, which brings its own image and artifacts. Choose the instance type (`ml.g5.xlarge` by default), the container image (the LMI/DJL vLLM deep learning container by default on the `s3://` route), volume size, timeouts and extra environment. Four resources are created per deployment (model, endpoint config, endpoint, and an inference component), cleaned up together on any failure. Scale to zero exists only through an inference component: `scale(n)` is `UpdateInferenceComponentRuntimeConfig` on the copy count, zero included, with managed instance scaling draining the instances behind it; automatic scale-out from zero (the Application Auto Scaling alarm AWS documents for that) isn't wired, so a scaled-to-zero endpoint comes back only when almyty next asks for copies. The bucket must live in, or be shared with, that AWS account; a MinIO or cross-cloud registry needs copying first. Cost is `hourlyRateCents` times observed instances, an estimate. An endpoint takes 8 to 15 minutes to come into service.

### vertex

Google Vertex AI, in your own GCP project, over two routes chosen by the reference. `vertex://publishers/<publisher>/models/<model>` or `hf://org/repo` takes Model Garden's one-call deploy, Google's own catalog and its choice of machine spec unless you name one. `gs://bucket/prefix` takes the Cloud Storage route: `models:upload` with `artifactUri` set to the prefix and a container spec that defaults to Google's own `pytorch-vllm-serve` image; Vertex requires an Artifact Registry or Container Registry image, so a Docker Hub image cannot be used here. Sources: `gcs` and `hub`; `s3://` is refused. Needs a service account key JSON with `roles/aiplatform.user` (or a short-lived access token), a project id and location (`us-central1` by default). A gated Hugging Face repository's token goes through `modelConfig.huggingFaceAccessToken` on the Model Garden route, straight to Google. Vertex never scales dedicated resources to zero on its current API (`minReplicaCount >= 1`), so `scaleToZero` is `false`: replicas 0 undeploys the model and keeps the endpoint at zero burn, and a positive count redeploys using the machine spec Model Garden originally chose. Teardown undeploys first, since Vertex refuses to delete an endpoint with a model still on it, then deletes the endpoint and the model. Cost is `hourlyRateCents` per replica times replicas, an estimate; Vertex publishes no per-endpoint cost API.

### azure-foundry

Microsoft Foundry, in your own Azure subscription, over three routes chosen by the reference. `foundry://{format}/{name}@{version}` takes a serverless API deployment against the Foundry catalog: Microsoft holds the weights, nothing to transfer, and the deployment resource names nothing container-shaped. `hf://{owner}/{repo}` takes a managed online endpoint fed from Azure's own Hugging Face registry (`azureml://registries/HuggingFace/models/{repo}/labels/latest`), with no environment and no image, so Azure's curated container serves it and Azure pulls the weights from the Hub itself; a gated repo needs the workspace's `HuggingFaceTokenConnection`, which the adapter does not create yet. `azureml://` or a blob `https://` URL takes a managed online endpoint over a registered model asset, the only route that names a container since Azure has no curated image for arbitrary weights; no registry URI or object-store key is ever sent on it. Sources: `hub` only; `s3://` and `gs://` are refused. Needs a subscription, resource group and workspace, and either a service principal or an ARM access token. The catalog route deletes the deployment on replicas 0 (which frees the quota) and recreates it at the configured token-per-minute capacity on a positive count; the two managed-endpoint routes have no scale to zero either (`scale(0)` deletes the deployment and keeps the endpoint URL). Cost is exact per-token pricing on the catalog route and `hourlyRateCents` times capacity over observed running time on the managed-endpoint routes; Azure's Cost Management API is not wired.

### runpod

RunPod Serverless, running RunPod's own first-party vLLM worker image. Needs a RunPod API key; choose the GPU type id, count, data centers, container disk, idle timeout, scaler type and value, and flashboot. Source: `hub` only: the worker's `MODEL_NAME` environment variable takes a Hugging Face repo id (or a path already inside the container), `MODEL_REVISION` pins a revision, `HF_TOKEN` unlocks a gated or private repo. RunPod has no secret store for serverless templates, so those go into the template's own environment; nothing secret is kept on the deployment's handle. `s3://` is refused with `ADAPTER_UNSUPPORTED_SOURCE`. Deploy creates a template and an endpoint pointing at it. Replicas are always-on workers: `scale(n)` sets the worker floor, and `scale(0)` sets both bounds to zero, the only way to stop an endpoint from answering; a floor of 0 with a positive ceiling reports `ready` with 0 replicas and cold-starts on the next request. Teardown deletes the endpoint, then the template. Cost is `hourlyRateCents` per worker times the larger of running workers and the floor; RunPod documents that billing endpoints exist but not their shape, so nothing from them is wired.

### digitalocean

DigitalOcean Gradient AI Dedicated Inference: a managed service DigitalOcean operates, serving a model on dedicated GPUs behind an OpenAI-compatible endpoint. **It is a DigitalOcean public preview**: enable it from the Feature Preview page in your control panel before you deploy, and expect the API to change. A token that works everywhere else on the DigitalOcean API is still refused here until you do, so that refusal is reported as `ADAPTER_PREVIEW_NOT_ENABLED` naming the opt-in rather than as a bad key, and the provider is labelled as a preview in the deploy form. Needs a DigitalOcean API token; choose the region (`atl1`, `nyc2`, `tor1`), the accelerator type and scale count (AMD MI300X, MI300X 8x, MI325X, MI350X; NVIDIA H100, H100 8x, H200, H200 8x, B300, B300 8x), and an optional VPC. Source: `hub`: a Hugging Face repository (`model_slug` with `model_provider: hugging_face`, and `access_tokens.hugging_face_token` for a gated repo), or a model already imported into DigitalOcean's own Model Catalog through Bring Your Own Model. BYOM import has no REST route: an operator imports once from the Control Panel (from Hugging Face or their own Spaces bucket), and the resulting catalog entry is named with `providerConfig.modelSlug`. Architecture is gated by DigitalOcean itself at create time (documented support includes `Qwen2ForCausalLM` and `Qwen3ForCausalLM`); an unsupported one comes back as `ADAPTER_UNSUPPORTED_ARCHITECTURE`. The create response returns a dedicated inference bearer token, which is the only credential the data plane accepts (not the account token) and is the only secret kept on the deployment's handle. Scale to zero is unverified and reported `false`: billing is per GPU-hour for the accelerators that exist, and only teardown reliably stops it. Cost multiplies the published per-accelerator hourly rate by the current scale; there is no usage API.

### nebius

Nebius Token Factory dedicated endpoints: an isolated, Nebius-managed deployment of a supported model template, not a compute VM. Needs a Nebius API token. Source: `hub`, narrowly: the repository must correspond to an existing Nebius model template (`model_name` plus `flavor_name`, taken from Nebius' own template list); anything else is refused by Nebius at create time. A fine-tune is named with `providerConfig.customWeightsId`: Nebius' Custom Weights Hub is support-gated beta with no upload API, so almyty can point at weights Nebius already holds but cannot register one itself. `s3://` is refused with `ADAPTER_UNSUPPORTED_SOURCE`. The data-plane host is derived from the region (`api.tokenfactory.<region>.nebius.com`), overridable through `providerConfig.dataPlaneHost` for a region whose host differs. Scale to zero PATCHes `{ enabled: false }`, since the minimum replica count can't go below one and this is the documented way to stop billing; a positive count PATCHes `{ enabled: true, scaling: {...} }`. Cost is `hourlyRateCents` per GPU per replica times the running count; Nebius publishes no usage API.

### stub

An in-memory adapter for development and the conformance suite, with no external product, API or bill behind it. Registered outside production, or in production with `MODEL_STUB_ADAPTER=true`. Its `simulate` field forces `quota_exceeded` or `fail_ready` outcomes for tests. There is no live suite for it and never will be.
