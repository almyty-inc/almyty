# Models CLI

`@almyty/models` manages your models from the terminal: list and add them, validate them, run a model on your own cloud account, and watch what it costs. It shares the login of every other almyty CLI.

```bash
$ npx @almyty/auth login
$ npx @almyty/models --help
```

The umbrella CLI exposes the same commands as `almyty models <command>`. Every command takes `--json` for raw output, `ALMYTY_TOKEN` to skip the stored login, and `ALMYTY_URL` to point at another almyty server.

## Models

List every model, or only the ones the router may pick:

```bash
$ npx @almyty/models list
Claude Sonnet  [claude-sonnet-5]  public  $3/$15 per M (feed:litellm)
    9b0d...  selectable
Qwen3 32B on our vLLM  [qwen3-32b]  private_cloud/eu-central  unpriced
    4f2a...  not selectable (validation: never)

$ npx @almyty/models list --selectable
```

Show one model:

```bash
$ npx @almyty/models get 9b0d...
```

Add a model against an inference provider, naming the vendor id yourself:

```bash
$ npx @almyty/models register \
    --name "Qwen3 32B on our vLLM" \
    --provider 7c1e... \
    --model qwen3-32b \
    --tier private_cloud \
    --region eu-central \
    --context 32768
Registered.
Qwen3 32B on our vLLM  [qwen3-32b]  private_cloud/eu-central  unpriced
    4f2a...  not selectable (validation: never)
Run: almyty models validate 4f2a...
```

A server you run (vLLM, Ollama, TGI, llama.cpp, LiteLLM) works the same way: it is a `custom` inference provider, set up once in the dashboard or with `POST /llm-providers` (see [A server you run](/models/providers#a-server-you-run)), and `--provider` names it. Its key lives on the inference provider, so no key is ever passed here.

Import what an inference provider currently lists, as unvalidated models:

```bash
$ npx @almyty/models sync 7c1e...
12 card(s) created, 3 already present.
```

Run the validation that makes a model selectable. The exit code is 1 when it fails:

```bash
$ npx @almyty/models validate 4f2a...
Passed in 812 ms.
Qwen3 32B on our vLLM  [qwen3-32b]  private_cloud/eu-central  unpriced
    4f2a...  selectable

$ npx @almyty/models validate 4f2a... ; echo $?
Failed: model qwen3-32b is not served by this endpoint
1
```

Remove a model:

```bash
$ npx @almyty/models delete 4f2a...
Deleted.
```

| Flag | Commands | Meaning |
|---|---|---|
| `--provider` | register | The inference provider's id |
| `--model` | register | The vendor model id sent on the wire. Not the model source that `deploy` takes below |
| `--tier` | register | `public`, `private_cloud` or `local` |
| `--region` | register | Region label used by routing allowlists. A model with no region is excluded by any policy that sets one |
| `--context` | register | Context length in tokens |
| `--selectable` | list | Only models the router may pick |

## Your cloud account

These commands run a model on [your own cloud account](/models/your-cloud). The command names and the `--adapter` flag keep the API's names: `deploy` starts a model, `deployments` lists the ones on your clouds, and `--adapter` takes the cloud's `providerType`.

List the clouds and what each can do:

```bash
$ npx @almyty/models adapters
modal  Modal
    architectures="any" lora="merged" serverless=true dedicated=false scaleToZero=true regions=[] registrySources=["hub"]
huggingface-endpoints  Hugging Face Inference Endpoints
    architectures="any" lora="merged" serverless=false dedicated=true scaleToZero=true regions=["us-east-1","us-west-2","eu-west-1","eu-central-1","ap-southeast-1"] registrySources=["hub"]
...
```

`--json` includes each cloud's `modelSchemes` (every source it accepts, as literal prefixes) and its config schema, the same data the **Add model** form renders from.

The model source is the **positional argument**. The cloud's account details carry secrets, so they come from a file, from stdin or from a saved connection, never from argv. Start a model from a Hugging Face repository:

```bash
$ cat > hf.json <<'JSON'
{"token":"hf_...","namespace":"acme","region":"eu-west-1","instanceType":"nvidia-a10g"}
JSON
$ npx @almyty/models deploy hf://Qwen/Qwen3-0.6B \
    --adapter huggingface-endpoints \
    --config-file hf.json \
    --desired '{"replicas":1,"region":"eu","privacyTier":"private_cloud"}' \
    --budget 5d3f...
Queued.
c07b...  huggingface-endpoints  pending  replicas ?/1
```

The model is in `list` at once, not yet selectable; validate it once it is running. Better still, connect the account once and name the connection, so no key reaches this machine's filesystem at all:

```bash
$ npx @almyty/models deploy hf://Qwen/Qwen3-0.6B \
    --adapter huggingface-endpoints \
    --credential 9b4c... \
    --desired '{"replicas":1,"region":"eu","privacyTier":"private_cloud"}'
```

Or a model the cloud already hosts:

```bash
$ npx @almyty/models deploy bedrock://anthropic.claude-3-sonnet-20240229-v1:0 --adapter aws-bedrock-import
```

`--config '<json>'` still exists, but `deploy` screens it against the cloud's config schema and refuses it the moment it carries a field the cloud marks secret: `token` for `huggingface-endpoints`, `tokenId` and `tokenSecret` for `modal`, `apiKey` for `fireworks` and the rest. argv is written to your shell history, is echoed by most CI runners and is readable by any process through `ps`, so a secret that travelled that way is disclosed. `--config` is also refused outright when the cloud catalog cannot be read, because then almyty does not know which of the fields are secret and will not guess. Run `adapters` to see which fields each one marks secret. `--config` is fine for the fields that are not secret, such as `namespace`, `region`, `instanceType` or `gpu`.

| Flag | Meaning |
|---|---|
| `<model>` (positional) | The model source: `hf://org/repo` (pinned to its exact commit for you; `@sha` pins one yourself), `s3://bucket/prefix@etag`, `gs://bucket/prefix@gen`, `file:///path@sha`, or a model the cloud already hosts: `bedrock://`, `sagemaker://`, `vertex://`, `foundry://`, `azureml://`, `fireworks://`, `together://`, `baseten://`. Required unless `--model-version` is given |
| `--adapter` | The cloud's `providerType`, from `adapters` (required) |
| `--config-file <path>` | The cloud's config read from a JSON file. The way to pass secret fields |
| `--config-stdin` | The cloud's config read from stdin. Same, for a secret that should not touch disk |
| `--config '<json>'` | The cloud's config inline. Refused if it carries a field the cloud marks secret, or if the catalog could not be read to check |
| `--credential <id>` | A connection made with `almyty connections connect`; the cloud's secrets are read from there instead of from any config you pass |
| `--desired` | JSON: `hardware`, `replicas`, `minScale`, `maxScale`, `quantization`, `region`, `privacyTier` |
| `--budget` | A spend budget; reaching it stops the model (scales it to zero) |
| `--card` | An existing model to attach instead of adding a new one; it gets the endpoint once ready and keeps being priced from the cloud |
| `--base` | The model family, when the cloud checks it and the source does not carry one |
| `--model-version` | A registered version instead of the positional source; see [Registered versions](#registered-versions) |

`adapters` lists what each cloud accepts; naming a source the chosen cloud can't read is refused before anything runs.

Watch state and spend:

```bash
$ npx @almyty/models deployments
c07b...  huggingface-endpoints  ready  replicas 1/1  spent 2.40 USD
e18a...  huggingface-endpoints  failed  replicas 0/1  spent 0.00 USD
    quota exceeded for nvidia-a10g in eu-west-1
```

`deployment <id>` shows one. Change the replica count (0 stops it) or shut it down. Both record what you want; almyty applies it at the cloud within two minutes:

```bash
$ npx @almyty/models scale c07b... 0
c07b...  huggingface-endpoints  scaling  replicas 1/0  spent 2.40 USD

$ npx @almyty/models teardown c07b...
c07b...  huggingface-endpoints  tearing_down  replicas 1/0  spent 2.40 USD
```

`teardown` removes the endpoint at the cloud. Weights are untouched: a Hugging Face repository, your bucket and a model the cloud hosts all stay where they are.

## Registered versions

Optional, and not needed to run anything: `deploy` takes the source directly and pins a Hugging Face repository for you. Register a version when you want a manifest digest, lineage and evaluation history recorded against your own weights, then pass `--model-version` to `deploy`.

```bash
$ npx @almyty/models versions
qwen3-14b-support-ft  qwen3-14b  29.00 GB  [bf16, awq-int4]
    a91c...  s3://acme-models/qwen3-14b-support@e3b0c442

$ npx @almyty/models register-version \
    --name qwen3-14b-support-ft \
    --uri s3://acme-models/qwen3-14b-support@e3b0c442
Registered.
qwen3-14b-support-ft  qwen3-14b  29.00 GB  [bf16, awq-int4]
    a91c...  s3://acme-models/qwen3-14b-support@e3b0c442
```

The URI must be pinned. An `s3://` version reads its base, size and quantizations from `almyty-manifest.json` at the URI (the format is in the [Models API](/api-reference/models-api#registered-versions)). For every other scheme the manifest is optional; pass `--base` when it is absent, and `--quantizations q1,q2` to record them.
