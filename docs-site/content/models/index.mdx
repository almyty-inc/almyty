# Models

An autonomous agent takes many steps, and not every step deserves the same model. A planning step wants the strongest reasoning model; a summary step wants the cheapest; anything that touches customer data may only leave the building on a private endpoint. almyty keeps one list of every model your organization can call, with its price, context length and capabilities, and lets each step pick a model or let almyty choose the cheapest one that fits.

There is one thing to set up: a **provider**. Connect a provider once and every model it serves appears in that list by itself. There is nothing to add per model.

```
Connect a provider  -->  key checked  -->  its models appear  -->  pick one, or Automatic
(OpenAI, Anthropic,      (one real call)    (price, context,         (in any agent, node
 your own server,                            availability)            or role)
 a cloud account...)
```

## Connect a provider

1. Open **Models** in the sidebar and click **Connect a provider**.
2. Find your provider in the grid: first-party vendors (OpenAI, Anthropic, Google Gemini, Mistral, xAI, DeepSeek, Cohere and more), hosted inference (Groq, Together, OpenRouter, Fireworks, Cerebras and more), clouds (Azure, AWS Bedrock, Vertex AI, Hugging Face, Modal and more), **Your own server** for anything OpenAI-compatible, and **Ollama**.
3. Paste the API key, or connect an account instead. Your own server and Ollama ask for the base URL and an optional key. A few providers ask for the one or two things they cannot work without: the region for AWS Bedrock, the resource and deployment for Azure, the project for Vertex AI.
4. **Who can use it** is everyone in your organization unless you change it to just you or a team.
5. Click **Connect**.

almyty checks the key right away with one real call and shows the models it found. If the check fails you are told why in one line, for example "OpenAI rejected this key.", with a link to the page where the provider issues keys; nothing is saved until the key works.

The provider is named after itself (rename it on its page later). There is no model id, privacy, region or context length to fill in: models come from the provider's own list, prices from the automatic price feed, and context length and capabilities from the same data. Anything you want to override lives under **Advanced** on the provider's page.

## The Models page

**Connected** shows one card per provider: its name, whether its key works, and how many models it serves. Click one to open the provider's page.

**All models** lists every model from every connected provider, grouped by provider and searchable, with:

- the price per million tokens in and out, and the context length
- whether it is available right now; if not, why: the provider no longer offers it, the provider said it is not available, or the provider's key check failed

With no provider connected, the page goes straight to connecting one.

## A provider's page

The provider's page shows whether its key works (with **Check again**), its models, the default model, who can use it, and **Replace key**. Everything else sits under **Advanced**: per-model overrides of price, context length, privacy tier, region and capabilities, an admin key for usage reconciliation, and default generation parameters. Removing a provider asks once and retires its models, which stay in past runs.

A cloud account provider (Hugging Face, Modal, AWS, Vertex AI, Azure and the like) also has **Start a model**: see [Your cloud account](/models/your-cloud).

## Choosing a model

Everywhere a model is chosen (an agent, a workflow step, a role, a provider's default) there is one search box that lists every available model, grouped by provider. Type part of a name to narrow it. **Automatic** at the top lets almyty pick per call: the cheapest model that fits the step, or the fastest, within the limits you set (see [Routing](/models/routing)). **Connect a provider** at the bottom opens the connect page in a new tab; the list refreshes when you come back.

## When a model is usable

A model is usable (the list offers it, the router may pick it) when:

1. it can be called: its provider is connected, or it has an endpoint URL;
2. it is active; and
3. it is checked: its provider's key check has passed.

The key check is one real call with the provider's key. When it passes, every model that provider lists becomes usable at once; there is no step per model. It runs when you connect the provider, when you change it, and when you click **Check again**.

Models stay current by themselves:

- **New models appear.** The provider's list is read again when you connect it, when you change it, on every passing key check, and every six hours.
- **Retired models leave.** A model the provider stops listing is marked "no longer offered" (`status: inactive`, `metadata.retiredReason: "not listed by provider"`). It is never deleted, because past runs point at it, and it comes back if the provider lists it again.
- **A model that stops answering leaves.** When a real call gets "model not found" from the provider, that model is marked unavailable at once, so nothing picks it again. Scheduled agents that used it pause and say which model to replace.
- **A key the provider refuses takes its models out** until the key is replaced and a check passes. An outage does not: the router just skips the provider while it is down.
- **A model on your cloud account** becomes usable by itself when it is running: almyty makes one short call through it as soon as the cloud reports it ready.

Nothing here is a hardcoded list. What almyty supports is whatever your connected providers serve.

## What a model records

This is the machine-readable record the router reads, returned by the [Models API](/api-reference/models-api):

| Field | Meaning |
|---|---|
| `name` | The label shown in lists |
| `providerId` or `endpointRef.url` | How the model is called: its provider, or the endpoint of a model on your cloud |
| `vendorModelId` | The id sent on the wire, for example `claude-sonnet-5` |
| `capabilities` | `tools`, `vision`, `reasoning`, `embedding`, `structuredOutput` as booleans |
| `contextLength` | Tokens of context |
| `privacyTier` | `local`, `private_cloud` or `public` (default `public`; `local` for Ollama) |
| `region` | Where the model runs, used by region allowlists |
| `pricing`, `pricingSource`, `pricingOverride` | Dollars per million tokens in and out, where the number came from, and an override that wins while set |
| `measuredLatencyMs` | `p50` and `p95` learned from real traffic |
| `status` | `active`, `inactive`, `error` or `deploying` (a model on your cloud that is still starting) |
| `validationStatus`, `lastValidatedAt`, `lastValidationError` | Whether the model is checked: `passed` once its provider's key check passed, `never` while it waits for one, `failed` when the provider said the model is not available |
| `selectable` | Whether it is usable right now (computed) |
| `base`, `modelVersionId` | For a model on your cloud: what it is based on, and its pinned source |

Every model belongs to one organization. Members can read models; connecting providers and editing models need the admin or owner role. A model served by another member's private provider is not shown to you.

## Privacy tiers

Tiers are ordered `local < private_cloud < public`. A routing policy names the most public tier a request may use, so a policy with `privacyTier: private_cloud` can pick a local model or a private-cloud model, never a public vendor. A vendor's models default to `public`, Ollama's to `local`, and a model on your cloud account to `private_cloud`. Change a model's tier under **Advanced** on its provider's page (`local` for a box in your office, for example).

## Pricing

Prices are automatic. A daily job (`MODEL_PRICE_FEED_CRON`, default 04:00) loads the LiteLLM cost map and cross-checks the OpenRouter models API. Models are priced from the cached feed when they appear and refreshed by the job. When the two sources disagree by more than 25 percent, the model keeps both numbers in `metadata.pricingDisagreement` so you can decide.

`pricingSource` says where the number came from:

| Source | Meaning |
|---|---|
| `feed:litellm` | The LiteLLM cost map |
| `feed:openrouter` | The OpenRouter models API |
| `native` | Reported by the provider itself (Together, OpenRouter) |
| `adapter` | The cloud's own cost report, for a model on your cloud account |
| `manual` | An override you set |
| `unpriced` | No source had a price |

An override (`pricingOverride`) wins over the feed until you clear it. A model with no price from any source is **unpriced**: the model says so, every run that used it says so, and the cost is never silently zero. Hosts that serve other authors' open models (Novita, DeepInfra and the like) are never billed at the original author's list price; without a feed quote such a model is unpriced. Your own server has no feed price either: give its models an override under **Advanced** if you want Automatic to weigh them, or leave them unpriced and the router places them last.

The router's `cheapest` objective ranks by a blended price, three quarters input and one quarter output per million tokens. Cost per run still uses the exact in and out prices; see [Cost governance](/cost-governance).

## Latency

`fastest` ranks by `measuredLatencyMs.p50`, which real traffic keeps current. After every routed answer the router folds the response time into the answering model: p50 as a moving average (a new sample weighs one fifth), p95 jumping to a slower sample at once and drifting back toward faster ones a tenth per sample. The estimate is written to the model at most once a minute and survives restarts. A key check that probed a model resets both to that single measurement.

## From the terminal and the API

```bash
$ npx @almyty/models list --selectable        # what can be picked right now, and why the rest cannot
$ npx @almyty/models sync 7c1e...             # read one provider's list again
```

Connecting a provider over the API is one call, `POST /llm-providers/connect`; see the [Providers API](/api-reference/llm-providers-api#connect-a-provider). Every command is in [CLI](/models/cli).

## Configuration

| Variable | Default | Meaning |
|---|---|---|
| `MODEL_CATALOG_BACKFILL` | unset | `off` skips the boot-time sync of providers that have no models, and the periodic sweep |
| `MODEL_CATALOG_SYNC_CRON` | `17 */6 * * *` | How often every provider's list is read again; `off` disables |
| `MODEL_PRICE_FEED_CRON` | `0 4 * * *` | Price feed refresh; `off` disables |
| `MODEL_RECONCILE_CRON` | `*/2 * * * *` | How often models on your cloud accounts are checked and brought to the state you asked for; `off` disables |
| `MODEL_ROUTER_VERIFY_ESCALATION` | unset | `true` lets a verifier rejection advance the route plan; see [Routing](/models/routing#verify-escalation) |
| `MODEL_STUB_ADAPTER` | unset | `true` registers the in-memory `stub` cloud in production too |
| `LLM_ALLOW_PRIVATE_URLS` | unset | `true` lets your own server sit on a private or loopback address (a vLLM box on the LAN) on a self-hosted API |
| `MODEL_REGISTRY_S3_*` | falls back to `STORAGE_S3_*` | Single-tenant seed of the one organization's bucket connection on first boot; ignored with more than one organization |
| `CONFORMANCE_LIVE` | unset | The `providerType` whose conformance suite runs against the real cloud |
