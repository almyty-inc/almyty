# Providers

A provider is a key almyty calls a vendor with. Add one and its models become [cards](/models) in the background; the first passing health check makes the default model selectable, and the router can pick it. almyty ships 31 provider types, and any server that speaks the OpenAI chat API can be registered without one.

![Models page](/screenshots/models.png)

Adding, testing and editing a provider in the dashboard is described in [AI Models](/llm-providers). This page is the vendor reference.

## Two kinds of vendor

- **Call-only vendors** host models and answer chat requests. almyty calls them with your key. That is every entry below.
- **Deployment providers** run weights you own or point at a platform's own hosted catalog. Those are [adapters](/models/deployments). A few names appear on both lists (Together, Fireworks, Baseten, Nebius, DigitalOcean, Modal) because the vendor both serves a call-only catalog and rents dedicated capacity.

DigitalOcean is the clearest case of both: Gradient Serverless Inference is a provider row here, call-only, no deployment involved. Gradient Dedicated Inference is a [deployment adapter](/models/deployments#digitalocean) that reserves GPUs. They are different products behind the same account.

## Verification

Every row below was checked against the vendor's current documentation on 2026-09-09, with a source URL per row in `docs/design/call-only-vendors.md`. Where a doc was ambiguous, an unauthenticated HTTP or DNS probe filled the gap. No live API key was used for any of it: nothing here was tested against a real account. Anything a vendor's docs do not state is marked "not documented" rather than assumed.

### Local and generic

| Type | Vendor | Default base URL | Auth | Live model list | Tools | Stream |
|---|---|---|---|---|---|---|
| `ollama` | Ollama | `http://localhost:11434/v1` | none (optional Bearer behind a proxy) | yes, native `GET /api/tags` | yes | yes |
| `custom` | Custom (any OpenAI-compatible server) | your `baseUrl` | per `custom.authMethod` | yes, `GET <base>/models` | operator's | operator's |

Every native type ships with its default base URL; set `baseUrl` to point at a compatible proxy instead. The key field takes whatever token the vendor issues and is encrypted at rest.

**Live model list.** Where the vendor serves a listing, the model dropdown is populated from it, a configured model is checked against it on save, and a blank model resolves to the vendor's current default by family, never a hardcoded id. Where no listing exists, a blank model resolves to `NO_MODEL_CONFIGURED` rather than a guessed id; the health check and the catalog surface the vendor's own reason when a request still fails.

**Dispatch.** Most types ride the OpenAI-compatible chat client: `<base>/chat/completions` with a Bearer key (or an `api-key` header for the two Azure surfaces). Anthropic, Gemini, Cohere, Perplexity, Vertex AI and Hugging Face have their own request shapes; nothing vendor-specific is added for a plain OpenAI-compatible host beyond its base URL, its auth header, its key page and its price-feed namespace.

### Notes per vendor

- **AWS Bedrock** answers through the `bedrock-runtime` OpenAI-compatible surface with a Bedrock API key sent as a plain bearer token. There is no SigV4 signing. Claude is not served on this surface: the API compatibility matrix lists ChatCompletions as unsupported for every Claude row on Bedrock, so Claude requires the native Converse or Messages API, which almyty does not call here. Models that do work include the OpenAI, xAI, Qwen, Z.ai and Writer families. Model ids are often inference profile ids (`us.`, `global.` prefixed), read from the live list rather than hardcoded.
- **Azure OpenAI** uses the `/openai/v1` data-plane surface with no `api-version` query string, and the key travels as `api-key`, not `Authorization: Bearer`, because on this surface a bearer token means an Entra ID token and fails. The listing is the resource's catalog, not its deployments, so the deployment name is still what you name as the model.
- **Vertex AI cannot use a static API key.** Google's docs state that only Google Cloud Auth works on this OpenAI-compatible surface; the credential is a service-account JSON key (or a pasted access token), and a short-lived OAuth token is minted per call. It serves no model list on this surface, so a model must be named at save time. Partner models on Vertex (Claude, Mistral, Grok, Jamba) run through Model Garden's native `:rawPredict`, not this surface, so `vertex_ai` only serves Gemini plus self-deployed endpoints. Llama on Vertex Model-as-a-Service is retired.
- **Qwen, Z.ai, SambaNova and Fireworks document no model listing** on their OpenAI-compatible surface. A model must be configured at save time; a failure resolves to `NO_MODEL_CONFIGURED` rather than a guessed id.
- **Azure OpenAI, Azure AI Foundry and Modal cannot be validated by key alone.** `model` is the customer's own deployment or endpoint name, so a valid key against nothing deployed still cannot answer. Modal in particular needs a Shared Endpoint created first from its own dashboard.
- **RunPod always carries an endpoint id in the URL.** There is no shared base URL: for the public catalog it is a shared model slug, for a private worker it is the customer's own endpoint id. Either way it is a required field.
- **DigitalOcean's tool calling is not documented** on the Gradient Serverless Inference surface, and streaming is only implied by "OpenAI-compatible" rather than shown in a documented example. **Nebius streaming is not documented** either, though the rest of the surface is OpenAI-compatible. None of these is asserted as working; the health check is what tells you.
- **Perplexity is Responses-shaped now**, not Chat Completions. The legacy Sonar chat-completions alias retires 2026-09-27; the Router API that would replace it is still private preview. The default base already targets the Responses-shaped surface a paying customer can use today.
- **Hosts that serve other authors' open models** (DeepInfra, Novita, Together, Fireworks, Baseten, Nebius, SambaNova, Cerebras, RunPod, Modal, OpenRouter) are priced from the feed under their own namespace. A DeepSeek model on RunPod is never billed at DeepSeek's list price; without a feed quote it stays unpriced. DigitalOcean, RunPod and Modal currently have no LiteLLM namespace at all, so models there are unpriced until one exists.
- **Usage reconciliation.** Only OpenAI and Anthropic document a usage or billing API almyty can ingest, so [cost governance](/cost-governance) cannot reconcile estimates against actuals for anything else.
- **Replicate** is not a provider type: its API is predictions-based and has no chat-completions endpoint to ride.

## Keys

A key belongs to one provider row, is encrypted at rest with the platform key (or your own KMS on Enterprise), and is never returned by the API. The provider form links to each vendor's key page. Vendors that offer a sign-in flow can be connected without pasting anything: OpenRouter mints a key scoped to almyty when you approve it. See [Connections](/connections).

## Any other OpenAI-compatible server

vLLM, TGI, llama.cpp, a LiteLLM proxy, a vendor that is not on the list: if it answers `POST <base>/chat/completions`, register it as a card. The URL and key become a `custom` provider row behind the scenes and the card points at it.

```bash
$ npx @almyty/models register-endpoint \
    --name "Lab box" \
    --url http://10.0.0.7:8000/v1 \
    --model qwen3-32b \
    --tier local \
    --region office
Registered.
Lab box  [qwen3-32b]  local/office  unpriced
    4f2a...  not selectable (validation: never)
Run: almyty models validate 4f2a...

$ npx @almyty/models validate 4f2a...
Passed in 640 ms.
Lab box  [qwen3-32b]  local/office  unpriced
    4f2a...  selectable
```

`--api-key` adds a Bearer token when the server checks one. A self-run server has no feed price, so give the card a price override if you want `cheapest` to weigh it, or leave it unpriced and let the router place it last. A server the reconcile loop should watch and price as a deployment is registered the same way and shows up under the `custom-endpoint` [adapter](/models/deployments#custom-endpoint).
