# Hosted chat app

Publish an agent as a branded, full-page chat at `https://<app-slug>.almyty.app`. There is no widget to embed and no separate frontend to deploy.

![A branded hosted chat app on its own address](/screenshots/apps-hosted-chat.png)

The page carries your app's name, colour, greeting, and AI disclosure. Visitors get streaming replies and conversation history without seeing the almyty dashboard.

## Publish from Apps

An app is the one place an agent is put in front of people, so the hosted chat is set up there and nowhere else.

1. Open **Apps** and create an app, or select one you already have.
2. On **Agents**, attach at least one autonomous agent and choose the default agent that answers.
3. On **Settings**, set the look visitors see once: name, colour, theme, greeting, suggested prompts and AI disclosure. Limits and visitor-data choices wait under **Advanced**, with their current values in one line.
4. On **Where people use it**, select **Add a place**, then choose **Web app**.
5. Select **Publish**. The link appears straight away: the app's name is the address.

The place changes to **Live** when the hosted chat is answering. Open `https://<app-slug>.almyty.app` to test it as a visitor.

![The web app page after publishing](/screenshots/apps-web-published.png)

The address comes from the app slug. It must be 3 to 63 characters, using lowercase letters, numbers, and hyphens without a hyphen at either end. Reserved service names cannot be used.

### On the web app page

Everything else about the web app is on the same page, each part saving as you go:

- **Who can use it**: one line, with the choices as tiles (anyone with the link, email verification, sign in with a provider, your SSO). The pick applies to the whole app.
- **Sign-in provider**, when people sign in with a provider: Google, Microsoft and GitHub first; **Other** asks for a discovery URL, and hand-entered endpoints, keys and scopes wait under **Advanced**.
- **Custom domain**: claim a hostname you own, publish the two DNS records shown, then verify.
- **Allowed sites**: the websites whose pages may call the chat from the browser.

A published web app is served by a gateway, and that gateway's page says **Managed in** the app, with a link back here, rather than carrying a second set of these settings. The hosted chat reads its look from the app on every request, so a change on **Settings** shows without publishing again.

## What a visitor gets

A visitor can start a chat, receive a streaming reply, and reopen earlier conversations. Public-link visitors do not need an almyty account. An anonymous visitor still has a separate record, keyed by a cookie scoped to that app's host, so one visitor cannot read another visitor's conversations.

Unpublishing turns the chat off without deleting its address or settings. Publishing it again restores the same distribution.

### Give the answering agent its product context

The app's name and greeting are presentation settings; they do not teach the agent about your product. Check the default agent on **Agents**, then configure that agent's instructions with its product scope, relevant policies, and how to handle missing information. Attach the tools or knowledge it needs before promising account-specific help.

Test ordinary visitor questions as well as connectivity: “What product do you support?”, a typical support request, and a request at the edge of the intended scope. A generic support-demo instruction can produce vague answers or unnecessary refusals even when chat delivery works correctly.

## What almyty stores about a visitor

A visitor on `{slug}.almyty.app` (or your own domain) is your user, not almyty's. So is someone who talks to the app through the widget on your website, one of its messaging channels, or its A2A endpoint. This is exactly what the platform keeps, where it goes, who can read it, and for how long. It applies to every place an app answers on.

**What is stored**

- **Who the visitor is**, as each place knows them:
  - Web chat: a visitor record with a random session key in a cookie scoped to that host, a truncated hash of the client IP (used only for rate limits; the address itself is not stored), and the time last seen. If the app requires sign-in, the record also holds the identity the sign-in returned: the provider, its subject id, the email and display name.
  - Website widget: a random conversation id, kept in the visitor's browser storage on your site. No cookie of ours and no record of the visitor beyond their conversation.
  - Messaging channel: the platform's own id for the sender (a Slack user id, a phone number, an email address), on each run.
  - A2A: nothing about a person. The caller is the credential it used (an API key or OAuth client), which counts only for rate limits.
- **Conversations and messages**: every visitor turn and every assistant reply in full, with the model used, token counts and cost, and any tool calls the agent made with their arguments and results. Each conversation is filed under the place it came from.
- **Runs**: the agent run behind each reply, with its input, steps, output and error, and the app it answered for (that is what the app's spend limit counts).
- **Widget replies**: the widget picks up its replies from a stored copy of each one, kept with the conversation id.
- **Nothing enters the agent's shared memory by default**, from any place. Visitor runs are not summarised into shared memory unless the app owner switches on **Include visitor conversations in memory**. When it is on, summaries may influence answers to other visitors.
- **Transient**: rate-limit counters (one hour at most) and the live event stream of a reply (minutes) in Redis.

**Where it goes**

- To the model provider you configured, under your API key, as the prompt. What that provider retains is governed by your agreement with them.
- To any tool the agent calls, as arguments.
- Nowhere else. Tenant chat hosts and the widget load none of almyty's product analytics or error reporting; those run only on the dashboard.

**Who can read it**

- Members of your organization whose role can open the agent: the runs tab shows each run with its input and output.
- Whoever operates the almyty deployment has database access to everything above. On almyty's hosted service that is almyty; on a self-hosted installation it is you.
- No one else. Another visitor cannot see it, and an unpublished app keeps its data but stops serving it.

**How long**

- Until you delete it, or until a retention period sweeps it. Settings, Organization, Data Retention sets independent periods for conversations and runs for the whole organization; the hourly sweep deletes records past the period and records what it removed in the audit log. With no policy set, records are kept indefinitely.
- An app can shorten that for its own visitors (see below). Its period covers conversations from every one of its places.
- Individual conversations and runs can be deleted per record from the dashboard.

**What you control, per app**

Every app carries these settings on its **Settings** tab, under **Advanced**, with defaults that need no attention:

- **Let visitors delete their data** (on by default). In the web chat the menu offers *Delete this conversation* and *Delete everything about me*; deleting everything removes the visitor record, every conversation and the runs behind them, the memories and files those runs wrote, and the stored replies, then reloads the page with a new private visitor identity. The widget on your website offers *Delete my chat*, pressed twice, which removes the same for that conversation.
- **Let visitors download their data** (on by default). The web chat's *Download my data* is a JSON file with the visitor record and every conversation; the widget offers *Download my chat*, the conversation as JSON, with its id (`threadId`).
- **Include visitor conversations in memory** (off by default): only switch it on for an agent whose memory is meant to learn from the public.
- **Delete visitor data after** a number of days (empty by default, meaning the organization policy applies). A value only ever shortens the organization policy; the hourly sweep removes older conversations, their messages and runs.

![The hosted chat privacy menu with export and deletion controls](/screenshots/apps-hosted-chat-privacy.png)

Switching a right off returns a plain refusal to the visitor with a stable code (`VISITOR_RIGHT_DISABLED`), and the widget stops offering the button; nothing is deleted or exported behind their back. Messaging channels and A2A have no self-service: someone who reaches the app that way asks you, and you answer from the app's page (below).

## How to answer a data request

Someone who messaged your app on Slack, Telegram, WhatsApp, SMS, email or another messaging app, or who runs an agent that calls it over A2A, cannot download or delete their own data: there is no page to put the button on. They ask you, and you answer from the app.

1. Open the app and go to **Visitor data**. Owners and admins see this tab; for anyone else the data requests do not exist, the same answer another organization gets.
2. Under **Where they used it**, pick the place they used. Only places that are published and talk to people are listed.
3. Type what that place knows them by, and **Look up**:

| Place | What to type |
|---|---|
| Web app | The email they signed in with, or the visitor id in the file they downloaded |
| On your website | The conversation id (`threadId`) in the file they downloaded from the widget |
| Slack | Their member id (`U012ABCDEF`): in Slack, their profile, then More, then Copy member ID |
| Telegram | Their Telegram user id (a number), not their @name |
| Discord | Their user id: with developer mode on, right-click them, Copy User ID |
| SMS, WhatsApp, Signal | Their phone number with the country code; spaces, dashes and a `whatsapp:` prefix do not matter |
| Email | The address they wrote from |
| Microsoft Teams, Google Chat, Matrix, IRC, Webhook | The sender id the platform sends (`29:…`, `users/…`, `@name:server`, the nick, or the `userId` your system sends) |
| Other agents (A2A) | The API key id or OAuth client id the calling agent used (either bare, or as `key:…` / `oauth:…`) |

4. The result says what the app holds for them, in counts and dates: conversations, messages with the first and last date, memories written for them, stored replies and channel deliveries, files, and runs, with their recent conversations listed. Nothing held means nothing to send or delete; check how the place writes the id first.
5. **Download their data** gives you a JSON file to send them: every conversation's transcript, the memories their conversations wrote, the stored replies to them, and the files and runs, by name and date. A channel's raw delivery is listed by date only, because the platform's copy also carries your workspace and bot ids.
6. **Delete their data**, confirmed once, removes everything tied to them in this app: the same things the web chat's *Delete everything about me* removes, on the place you picked. The runs they started are removed with the runs those started, and nothing of another person, another app or another organization is touched.

Each download and each deletion is written to the audit log (**Analytics**, **Audit**, filter by *Visitor data sent* or *Visitor data deleted*): who answered, which app and place, and the counts. The person is recorded as a hash of the place and what you typed, never the id itself, so an auditor holding the id can find the entry and the log holds no phone number or address. If the audit row cannot be written, nothing is exported or deleted.

What this covers and what it does not:

- It covers what almyty holds for the app. Copies the messaging platform keeps (the Slack workspace's own history, the email in your inbox) are yours to handle on that platform.
- A group thread on a messaging channel is filed under the person who started it; messages someone else added to that thread go with it.
- Memories exist only when the app lets visitor conversations reach memory, and are found by the run that wrote them. Memories synced to an external memory provider are removed there by that provider's own tools.
- A person who used two places (the web app and Slack) is two look-ups.


## Protect model spend

Every place an app answers on (web chat, website widget, each messaging channel, A2A) applies the same limits, read from the app on every message:

- **Spend limit per run**: a run that would cost more is stopped rather than billed. Starts at 0.50.
- **Messages per visitor, per hour**, counted for each visitor on their own: the web chat visitor, each widget conversation, each messaging-channel sender, each A2A credential. Starts at 60. A burst limit of a fifth of that per minute (at least 3) stops an hour's share going in seconds.
- **Messages per IP address, per hour**, for the places that see the visitor's address (web chat, widget, A2A). Starts at 120. A messaging channel's webhooks come from the platform, not the visitor, so channels are limited per sender only.
- **Spend limit per day** and **per month** for the whole app: every place and every visitor together. An app open to anyone starts at 5 a day and 50 a month; an app only your directory can reach (SSO) starts with none. Days and months start at midnight UTC.

These are rate and cost limits for each visitor and for the app, never one shared bucket built from a per-visitor number.

When the app reaches its daily or monthly spend limit, no place answers a new message until the limit resets or you raise it. Visitors are told, in plain words, **This app has reached its limit for today** (or *for this month*): the web chat and the widget show it in place of a reply, a messaging channel sends it as the answer, and an A2A caller gets it with the code `APP_SPEND_CAP_REACHED`. The app's page says the same thing with what it spent, and owners and admins get a notification once per period.

The spend limit counts the cost the app's runs have recorded. A conversation already under way when the limit is reached finishes under its own per-run limit, so the app can go over by at most one run's limit per conversation running at that moment. A conversation that stays open across midnight counts in full on each day it is active.

An app open to anyone (anyone with the link, email verification, or OAuth) cannot be published until the per-run limit and both rate limits are set. The distribution page names each missing setting before the app can go live, so a public URL cannot spend against your model keys without a ceiling.

Email verification and OAuth still let anyone with an inbox or an account in, so they keep every limit above. Only SSO, where your own directory vouches for everyone, is gated; it requires a commercial entitlement.

## Addresses in each environment

Hosted apps and the dashboard use separate domains:

| Environment | Dashboard | Hosted app |
|---|---|---|
| Production | `app.almyty.com` | `<app-slug>.almyty.app` |
| Staging | `app.staging.almyty.com` | `<app-slug>.staging.almyty.app` |
| Development | your development dashboard | `<app-slug>.dev.almyty.app` |

Keeping the app on its own host lets the visitor cookie stay scoped to that app instead of the dashboard or API.

## Self-hosting

Hosted chat is part of the Apache-licensed core. To serve apps on a domain you control:

1. Point a wildcard DNS record at your deployment, for example `*.chat.acme.com`.
2. Set `HOSTED_CHAT_BASE_DOMAIN=chat.acme.com` on both the API and frontend containers. The frontend reads it at runtime, so the same image can be used in every environment.
3. Route `/api` on every tenant host to the API and strip the `/api` prefix. Route every other path to the frontend. Keeping these calls same-origin is what keeps the anonymous visitor cookie on the tenant host.
4. Issue a wildcard certificate for the domain and attach it to the tenant-host ingress.

An app with the slug `support` is then available at `https://support.chat.acme.com`.

### Wildcard certificates need DNS-01

Let's Encrypt does not issue wildcard certificates through an HTTP-01 challenge. Use DNS-01, which means your certificate controller needs permission to create TXT records in the zone. If your issuer has no solver for that DNS provider, move the zone or delegate `_acme-challenge` to one it can update.

A certificate per tenant also works, but Let's Encrypt limits issuance to 50 certificates per registered domain each week.

## What is commercial

Two options require a commercial entitlement:

- removing the almyty mark with white-label mode; and
- using SSO as the app access mode.

Public links, email verification, and OAuth remain in the core edition.
