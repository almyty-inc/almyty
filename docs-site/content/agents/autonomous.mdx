# Autonomous Agents

Give an agent instructions, a set of tools, and a goal. It decides which tools
to call and how to answer, with no pipeline to draw. Several models can
collaborate inside one agent, the output is checked before it returns, and the
agent carries memory and constraints from one run to the next. (For the opposite
approach, where you wire each step yourself, see [workflow agents](/agents/builder).)

![Autonomous agent detail](/screenshots/agent-detail-overview.png)

You configure all of this on the agent's detail page. To run one from your
terminal:

```bash
$ npx @almyty/agents run support-orchestrator \
    --input '{"ticket": "Where is my order #4821?"}' --watch
```

`--watch` streams each step (tool calls, verifier verdicts, revisions) as the run
unfolds. See the [Agents CLI](/cli/agents) for the full command set.

## Work mode: how it works, and which models do it

The **Work mode** section comes first on the agent's edit page. Pick the mode
from the dropdown, and the model slots under it follow from the mode: each
slot asks for exactly the model that mode needs.

| Work mode | What happens | Slots it shows |
|---|---|---|
| **Single** | The main model does it all. | Main |
| **Cascade** | A cheaper model answers first and a checker double-checks it; the main model steps in only when the check fails. | Drafter, Checker, Main |
| **Best of N** | The main model writes several answers and the checker picks the best. You set how many (2 to 5). | Main, Checker |
| **Panel** | Panelists answer too, and a judge writes one answer from all of them. | Main, two or more Panelists, Judge (optional) |
| **Explore, extract, patch** *(experimental)* | Explorers look around with the tools, a summariser sums up what they found, the main model works from that, and a checker checks the answer. | Explorers, Summariser, Main, Checker |

Each slot picks its model the same way as everywhere else in almyty: one
searchable list of the models your connected providers offer, or
**Automatic**, which routes each call by policy. A panelist can instead be
another of your agents, answering with a run of its own. The **Judge** is
optional: without one, the main model judges the panel. A judge is always a
model.

Switching the mode keeps what you picked for the other slots while you edit,
so switching back brings them back; a save keeps only the slots the chosen
mode uses. Each slot's name, temperature, token limit and extra instructions
sit under its **Advanced**. Under the section's own **Advanced**, add other
models the main model can hand a piece of work to, in any mode. Other agents
it may call are picked under [Capabilities](#capabilities).

Whatever the mode, the visitor, the API caller or **Try it** gets one answer:
the checked draft or the main model's fix, the picked answer, the judge's
answer, or the main model's answer from the brief. Each step on the run
records which role took it and which model answered, including, for an
automatic slot, what the router picked and why.
## Verification

Open the **Models & Verification** panel and click **Configure** to set up
verification: add reviewer models (each with its own provider and focus
instructions), choose how their verdicts combine, decide when they run, and set
how many times the agent may revise.

Use **Configure verification** on the agent's Overview tab to edit the verifier panel inline, then **Save verification**.

Reviewers are refute-only: each tries to find a reason the answer is wrong. How
their verdicts combine:

| Policy | The answer passes when |
|--------|------------------------|
| All pass | every reviewer approves |
| Majority | most reviewers approve |
| Any fail blocks *(default)* | a single failure blocks it |

When verification runs:

- **On final output** is a gate. The answer is reviewed before it returns. On a
  failure the agent gets the feedback and revises, up to the revise budget
  (default two), then completes. The run records the verdict, how many revisions
  it used, and whether it ran out of budget.
- **Mid-run** (every N steps, or after a tool result) is advisory: it injects a
  course-correction note without ending the run, so the agent can adjust before
  going further.

Workflow agents get the same capability as a verify node; the logic is shared
between the two modes.

## Capabilities

**Capabilities** says what the agent may use and reach while it works.
Anything it is not given here is refused when its model asks for it, with
nothing run.

- **Tools and APIs**: pick single tools, or tick **All tools** on an API. An
  API picked this way gives the agent every active tool of it, including
  tools added to the API later.
- **Other agents it can call**: tick the agents it may hand work to. Its
  model is offered each one as a tool and gets that agent's answer back. No
  other agent is reachable; with none ticked, it calls none.
- **Machine**: the labels of the machine its runner tools run on, such as
  `gpu=yes`. The page lists the machines that carry them. Work goes only to
  an online machine with all of the labels; see
  [Send work to a matching machine](/runner#send-work-to-a-matching-machine).
- **Temporary agents**: let it create helper agents for part of a task, with
  a limit per run and a limit on how many may exist at once across its runs.
  A helper only gets tools this agent has, and is removed when its run ends.

Several models working together inside one agent is the
[work mode](#work-mode-how-it-works-and-which-models-do-it); several agents
working together is this list.
## Constraints

Constraints are per-agent rules that keep an agent from repeating mistakes. Add
them on the agent's **Constraints** tab, or let the agent learn them: when a run
fails, the lesson is distilled into a new constraint automatically. Active
constraints are always-on, applied on every run, which makes them distinct from
[memory](/memory), which is recalled by relevance.

![Constraints tab](/screenshots/agent-constraints.png)

For the Support Orchestrator the active rules read like "never promise a refund
over $500 without approval," "Scale-plan customers get a four-hour SLA," and
"keep replies under 150 words." A blocked run can add its own: "a run was blocked
for issuing a $900 refund without approval, gate refunds over $500."

## Promote a run to a skill

When a run goes well, expand it on the **Runs** tab and choose **Promote to skill**. Fill in the inline form. almyty
distills the run (its tool sequence and output) into an
[Agent Skills](https://agentskills.io) `SKILL.md`, stored and versioned. From the
**Skills** tab you can view it, replay it, or delete it. The skill is served over
the [Skills gateway](/gateways/skills) and REST, so another agent, or your editor
via [`@almyty/skills`](/cli/skills), can call it instead of re-deriving the steps.

![A promoted skill's SKILL.md, distilled from a run, with the tool procedure](/screenshots/agent-skill-viewer.png)

A reasoning-only run produces the procedure in prose; a run that called tools
lists them in order ("1. Look up order status, 2. Search the knowledge base, ..."),
so the skill captures the real steps.

## Memory

Turn on **Remember between conversations** and the agent looks up what it
saved earlier before it answers. Then choose:

| Setting | Choices |
|---|---|
| **Memory account** | almyty's own memory, an outside memory account (Mem0, Zep, Supermemory and others) your organization has set up, or an account of the agent's own: anyone who can edit the agent can connect one with **Add a memory account**. |
| **Whose memory** | **Each person has their own**, **This agent's own**, or **Shared by all agents**. |
| **What it saves** | **Facts it learns** (after each conversation, the agent's main model picks out what is worth keeping), **Whole conversations** (each exchange as said), or **Only when asked**. |
| **Never save** | Rules, one per line, such as "payment details". Every save is checked by the agent's main model first, and what the rules cover is taken out. |
| **How long it keeps memories** | **Until deleted**, or **For a number of days**. |

See [Memory](/memory#an-agents-memory-settings) for what each setting does
at run time.
## Context compaction

Long runs can outgrow the model's context window. Turn on compaction and almyty
keeps the run bounded: once it goes over a token budget, the older history is
folded into a cached summary while the recent messages are kept verbatim. It runs
automatically; there is nothing to watch.

## Create an autonomous agent

In the UI: **Agents -> Create Agent -> Autonomous**. Write the instructions,
pick the work mode and the models for its slots, then set memory and
capabilities, all on one page. Constraints and the verifier panel are on the
agent's own page once it is saved.

![Autonomous agent form in the builder](/screenshots/agent-builder-autonomous.png)

Once it is active, invoke it from the terminal with
`npx @almyty/agents run <name> --input '{...}'`, or from any client via the
[OpenAI-compatible API](/api-reference/openai-compatible).
