# Credentials

**Credentials** is where almyty keeps every key, token and signed-in account it uses on your behalf: the keys your APIs and tools send, chat channel tokens, memory service accounts, MCP server tokens, cloud accounts, model buckets and model provider keys. Each one is added once and used anywhere. The secret itself never leaves the backend, and it is never shown again after you save it.

![The Credentials page: every key in one table, with model provider keys as their own group](/screenshots/credentials-vault.png)

## The Credentials page

Open **Credentials** in the sidebar (`/credentials`). One table lists every credential, with:

| Column | What it says |
|---|---|
| **Name** | The name you gave it, with the service's logo |
| **Service** | What it signs in to (GitHub, Slack, "Other service"), or what kind of key it is |
| **Status** | **Works** when the service accepted it at the last check, **Needs attention** when it did not, **Saved** for a key nobody can check (a plain key under "Other service") |
| **Who can use it** | **Everyone** in the organization, or **Only you** |
| **Used by** | What uses it: an API, a tool, an MCP server, a channel |
| **Added** | When it was added |

Model provider keys (OpenAI, Anthropic and the rest) are listed below as their own group, **Model providers**. They are added and changed on [Models](/models/providers), where their models come with them.

Click a row to open the credential's own page. Admins also get an **Advanced** tab (see [Advanced](#advanced)).

## Add a credential

1. Click **Add credential** (`/credentials/new`).
2. Pick the service's tile, or search for it. For a key the list does not know, pick **Other service** (or, when a search finds nothing, **Save its key as another service**).
3. Give it the one thing it needs: a key, or a sign-in at the service. A link next to the field goes to the page where the key is made.
4. **Who can use it** starts at everyone in your organization; **Change** makes it yours alone, when your organization allows personal keys.
5. Click **Save** (or **Sign in**). The key is checked with the service before it is kept; a refusal is said in plain words next to the key, and the form stays filled.

A model provider tile leads to [Models](/models/providers), where the provider and its models are set up together.

### Ways a service is added

Each service offers one or more ways, best first; the others wait under **Advanced** on its form:

| Way | What you do | What is kept |
|---|---|---|
| Key | Paste the key; the form links to the page where it is made | The key and any plain fields, such as a base URL |
| Sign-in | Sign in at the service and approve. Nothing to paste | The key or token the service issues |
| App client | Paste a tenant, client id and secret (Azure) | Those three, the secret encrypted |
| Cloud role | AWS: a CloudFormation quick-create link makes a role in your account that trusts almyty with an external id, no long-lived keys | The role ARN |
| Service account | Upload a service account JSON (Google Cloud) | The JSON, encrypted |
| App install | A Slack-style app install | The installation token |

A key is checked against the service before it is saved: `GET /models` for most model providers, a whoami for Hugging Face and DigitalOcean, STS for AWS, a token grant for Google Cloud and Azure, a `HeadBucket` for a bucket, an `initialize` for an MCP server. From a terminal or a machine without a browser, a sign-in can finish with a code the service shows you: paste it under **Advanced**.

## Pick one or create one where it is used

You rarely need to open Credentials first. Wherever almyty needs a key, the field is the same control: **pick one of your credentials** from the list, or click **Create one here** to add it right there, in the form you are filling in, without losing what you typed. What you create lands on the Credentials page like any other credential, comes back already picked, and an **Open** link next to the field goes to its page (in a new tab).

The control is on:

- **Finish connecting** an API and the API's **Key** card: the key its tools send. How it is sent (the header, bearer, basic, OAuth 2.0) comes from the API's description and is a **Change** away. A username and password for basic auth are typed there; an OAuth 2.0 API signs in there.
- **Create tool**: the API key or bearer token of an HTTP tool. The tool keeps only which credential it uses; the key is read from Credentials when the tool runs, as whoever runs it.
- **Add MCP server**: the server's token.
- **Memory**: the account an outside memory service signs in with.
- Chat channels and model providers, with their own forms.

## A credential's page

`/credentials/:id` shows the credential's name, service and account, whether it works, and **Check again**. Its tabs:

- **Overview**: the account, the key (stored encrypted and never shown again; **Replace key** swaps it in place, so everything that uses it keeps working), who can use it, and **Delete credential** behind a one-line confirm. Deleting revokes the key at the service first when the service allows it; otherwise revoke it there too.
- **Used by**: what uses it.

A key that one API, MCP server, channel or app keeps for itself (a username and password typed on an API, for example) is listed too. Its page says what keeps it, with a link there to change it.

## Organization or personal

A credential belongs to the organization or to you.

- **Organization credentials** are what agents and models on your cloud accounts use. Adding one needs the `connections:manage` permission (admins and owners).
- **Personal credentials** are your own keys, when the organization allows them: on by default for free and personal organizations and off for production organizations. An admin turns it on or off under **Credentials → Advanced → Personal keys**.

Everyone sees the organization's credentials; a personal one is visible to its owner and to admins. Who may *use* a credential in a run, beyond its owner, is decided by [who can use it](/credentials/grants).

## Advanced

Admins get the **Advanced** tab (`/credentials/advanced`):

- **Who can use each credential**: narrow an organization credential to people, teams, roles or agents. See [Who can use a credential](/credentials/grants).
- **Personal keys**: whether members may add keys only they can use.
- **Custom services**: services the list does not have, such as any OpenAI-compatible endpoint, MCP server, memory service or bucket. A custom service has the same shape as a built-in one: a key, a kind, the form with secret fields marked, and how it is checked.
- **Governance**, for organizations with the `credentials_governance` entitlement (Business and Enterprise):
  - **Allow and deny lists**: which services may be added at all, for organization credentials, personal ones, or both.
  - **Scope rules**: what an agent, workspace, user, team or role may use, optionally only in some environments (an agent tagged `production`, for example); a rule can require organization credentials from approved services only.
  - **Expiry rules**: a secret older than a maximum age is expired, owners are warned ahead of time, and with enforcement nothing keeps using it.
  - **Rotation rules**: replace keys on a schedule through the service's API where it supports that, with the owner told to replace it by hand where it does not.
  - **Budgets**: a use whose spend budget is exhausted is refused before the secret is decrypted.
  - **Review** of personal credentials granted to agents, and an **audit export**.

## Where secrets live

Secrets are stored in one place, the organization's credential store, encrypted with the platform key or, for organizations that bring their own KMS, with their key. They leave the backend only inside the request to the service they belong to. Every URL a check probes passes the SSRF guard; private ranges are allowed only for services with an explicit opt-in (`OLLAMA_ALLOW_PRIVATE_URLS`, `MCP_ALLOW_PRIVATE_URLS`). Every add, check, key replacement, delete, grant, revoke and use is written to the audit log with the service, the way it was added, the owner and the outcome.

## Access keys

Keys that let a client call *your* gateway or agent are not credentials: they live on the gateway or agent they unlock. See [Gateway authentication](/gateways/authentication).
